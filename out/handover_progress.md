## 기록

## [A] 미커밋 마무리 — 넣었다

`app/engine/pipe_graph.py` 의 `dead_ends` 순서 비결정성.

- 원인: 방문 노드 **집합(`seen`)을 그대로 순회** → 파이썬 문자열 해시가
  프로세스마다 섞여 뒤따르는 `[:40]` 이 **어느 40개를 남길지**가 갈렸다.
- 검증: 해시 씨앗을 달리한 두 프로세스(`PYTHONHASHSEED=1` / `999`)로 전량 2회
  - 지문 **015e34b3** 동일 · **1037행** · **Q'ty 1931** 동일
  - `trace` 가 있는 1037행 중 **순서까지 다른 행 0** (17회차 실측 282)
- 빠른 시험 188 통과 · 실 DB sha256 `643748dc…` 불변 → **커밋 `d700eed`**

**즉 비결정성 제거가 결과를 바꾸지 않았으므로 꾸러미에 넣는다.**

## [B] SADARA 교차검증 — **기준선과 같다 (0767ba79 · 82행)**


### ★ 안 움직인 이유를 규칙별로 쟀다 — "안 걸렸다" 가 아니다

| 새 규칙 | SADARA 에서 무엇을 했나 | 행에 닿았나 |
| --- | --- | --- |
| [E] 범례 p2 **ANGLE 몸체** | **실제로 발동한다** — p7 에서 도형 3개가 정의에 걸리고 몸체 **2개**가 섰다.  켬/끔 대조: `CHECK 37 → 35` · `ANGLE 0 → 2` (CHECK 로 잘못 읽히던 삼각형이 접혔다 — AL NOUF1 과 같은 모양) | **닿지 않았다** — 둘 다 `actuator=NONE` → `EXCLUDED`.  **CHECK 였을 때도 EXCLUDED** 였으므로 행 수도 지문도 그대로다 |
| [C] **그 장에서 별표 크기 재측정** | **아무 것도 추가하지 않았다** — 분석 9장 **전부**에서 새로 받아들인 크기 **0**.  이 도면은 범례 크기와 도면 크기가 일치한다 (AL NOUF1 p35 같은 사례가 없다) | 닿지 않았다 |

**결론**: ANGLE 규칙은 **다른 프로젝트에서도 도형을 잡고**(범용성 확인),
**액추에이터가 있어야 산출물에 들어가므로 행을 함부로 늘리지 않는다**(안전).
별표 재측정은 **더하기만 하는 규칙**이라 그런 도면이 없으면 아무 일도 없다.

### ⚠ 그 김에 발견한 것 (이번 꾸러미와 무관 · 고치지 않음)

**이전부터 그랬고 이번 변경과 무관**하다.  AL NOUF1 은 범례에서 유닛 승수를

## [E-2] 파일명이 알집에서 깨진 것 — 재포장

**증상**: 회사 PC 의 알집에서 바깥 세 파일이 `1_?쉽??쎄린_README.txt` 로 보인다.

**원인**: 바깥 zip 을 리눅스 `zip` 으로 만들어 **UTF-8 플래그가 안 붙었다**
(실측 `flag=0x0000`).  이름은 UTF-8 바이트인데 Windows 는 CP949 로 읽는다.
**안쪽 40개는 전부 영문 경로라 무사했다** (비ASCII 이름 0건 — 실측).

**고친 것 둘.  둘 다 "플래그를 믿는" 대신 "깨질 수 없게" 하는 쪽이다.**

1. 바깥 세 이름을 **영문**으로 — `1_README_FIRST.txt` · `2_FILE_LIST.txt`
   · `3_OVERWRITE_FILES.zip`.  압축 프로그램이 무엇이든 안 깨진다.
2. 두 txt 를 **UTF-8 BOM** 으로 저장.  Windows 메모장이 UTF-8 로 열게 한다
   — 이름을 고쳐도 **본문 한글이 깨지면 같은 신고가 다시 온다.**

**재검증은 하지 않았다 — 할 필요가 없다.**  안쪽 `3_OVERWRITE_FILES.zip` 의
sha256 이 `c6cb177d…` 로 **바뀌지 않았고**(이름만 바꿔 담았다), 안쪽 40개가
현재 트리와 바이트로 같은 것을 다시 확인했다.  12단계 검증은 그 안쪽 zip 을
푼 것이므로 그대로 성립한다.

바깥 zip 은 `zip` CLI 가 아니라 **파이썬 `zipfile`** 로 만든다 (이름 검사를
`assert` 로 걸어 두어, 비ASCII 이름이 섞이면 만들다 멈춘다).
