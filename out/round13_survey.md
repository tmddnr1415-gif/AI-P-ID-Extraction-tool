## B3. 첫 화면에서 그것에 닿을 수 있는가 — 닿기는 하나, 무엇인지 알 수 없다

**있다**: 첫 화면 카드 아래 `#joblist` "이전 분석" 목록. 클릭하면 `#<job_id>`

**문제는 목록이 말하는 내용이다.** 실측 캡처(`out/round13/c1_joblist.png`):

  **새 PDF 를 넣을 자리**이지 **저장된 결과를 여는 자리가 아니다.**

즉 **서버는 다 갖고 있고 화면이 그것을 말하지 않는다.**

## B4. 사용자 편집이 저장되는가 — 열별 실측

`db.EDITABLE` 10열 전부에 대해 편집 → 저장 → **서버 재기동** → 재조회했다.

| 열 | 편집 | 저장 | 재기동 후 유지 |
| --- | :--: | :--: | :--: |
| `description` · `scope` · `qty` · `type` · `system` | ✓ | ✓ | ✓ |
| `vendor_supply` · `tag_no` · `valve_type` · `remark` · `description_grade` | ✓ | ✓ | ✓ |

- 저장 경로: `PATCH /jobs/{id}/rows/{key}` → `db.set_user_value` →
  `item.user_json`. **`ai_json` 은 건드리지 않는다.**
- 실측: 편집 9칸 후 `ai` 층이 그대로였다 —
  `type` FIT / `qty` 2 / `scope` `VENDOR(HRSG)` / `remark` `타사 공급 …` 보존.
- **되돌리기가 이미 있다**: 빈 값으로 PATCH 하면 `user_json` 에서 그 칸이
  빠지고 화면은 AI 값으로 돌아온다 (실측 확인).
- **편집 표시도 이미 있다**: `td.edited` 가 초록 글자 + `✎`.
  실측 캡처에서 9칸에 표시됐다 (`out/round13/d2_edit_after.png`).
- **⑤ 측정 오염 없음**: 편집 9칸 후 `job.fingerprint` = **`69ad281f` 그대로**.
  지문은 분석 시점에 굳고 편집 경로가 닿지 않는다.

**`axis_overrides.json` 은 Description 전용이다.** ④ 행의 FROM/TO 확정만
담고(키 = 안정 ID), 프로젝트 폴더에 산다. 다른 열은 담지 않는다.

**⚠ 그래서 한계가 하나 있다 — 편집은 job 안에서만 산다.**
`user_json` 은 `(job_id, key)` 에 매여 있으므로 **다음 Rev(=새 job)로는
넘어가지 않는다.** 넘어가는 것은 `axis_overrides` 를 통한 **Description 하나**
뿐이다 (`_run_comparison` 의 승계 훅).

## B5. 재분석하면 편집값은 어떻게 되는가 — 유지하고, 갈리면 알린다

`db.store_result` 가 이미 정한다 (코드 주석 그대로):

1. `user_json` 을 **그대로 둔다** — 재분석은 `ai_json` 만 갈아 끼운다.
2. 사람이 덮어쓴 칸에서 **엔진의 새 답이 이전과 다르면** `conflict_json` 에
   `was_ai` / `now_ai` / `user` 세 값을 남기고, 그 행의 `needs_review` 에
   `re-analysis changed … under an edit you made` 를 붙여 검토로 보낸다.
3. **묻지 않는다** — 양쪽 값을 다 들고 사람에게 보인다.

즉 [D] 의 "두 안을 내고 사용자가 정한다" 는 **이미 3번으로 정해져 있다.**
남는 판단은 "이 정책을 유지할지" 하나다.

## B6. Rev 판별 — 읽기는 되고, 저장이 안 되고, 프로젝트 Rev 와 다른 축이다

**읽는다.** `app/engine/extract_titleblocks.py` 가 REV 칸을 **글리프 단위로**
읽는다 (개정 이력 행 수를 세지 않는다 — 그 방법이 안전하지 않다고 파일 머리에
적혀 있다). 형식은 config `formats.revision: '^[A-Z][0-9]?$'`.

**AL NOUF1 실측 (58장 전수 · 신뢰도 전부 HIGH)**

| rev | 장수 | | 판독 방법 | 장수 |
| --- | ---: | --- | --- | ---: |
| A | 15 | | GLYPH | 48 |
| A1 | 1 | | TEXT | 10 |
| B | 19 | | | |
| C | 16 | | rev_date 있음 | 9 |
| D | 7 | | rev_date 없음 | 49 |

PID 53장만 보면 A 11 · A1 1 · B 18 · C 16 · D 7.

**⚠ 여기서 세 가지가 갈린다.**

1. **문서 단위 Rev 가 없다.** 장마다 다르다(A~D). "이 PDF 의 Rev" 를 하나로
   정하려면 대표값 규칙(최빈? 최대? 표지?)이 필요한데 **도면에서 유도되지
   않는다.** 임의로 정하면 §2.1 ③ 위반이다.
2. **읽은 값이 저장되지 않는다.** `pid_page` 에 `rev` 열이 없고
   `engine_json` 에도 없다(키: multipliers · legend · glyphs · job_review ·
   applied_rules · timings · pipe_trace · description_*). 분석 결과 json
   안에는 `titleblocks` 로 들어 있으나 DB 로 넘어가지 않는다.
   **→ 지금은 분석이 끝나면 Rev 를 다시 볼 수 없다.**
3. **프로젝트의 Rev 는 도면 Rev 가 아니다.** `revisions.next_revision()` 은
   등록된 리비전 **개수**로 `Rev.A → Rev.B …` 를 붙인다. 도면이 Rev.C 여도
   그 프로젝트의 첫 분석이면 `Rev.A` 다.

**따라서 [E] 는 조건부다.** 장 단위 Rev 대조(같은 도면번호의 rev 가 이전
리비전보다 나중인가)는 **근거가 있다**. 문서 단위 "이 PDF 는 Rev.C 다" 는
**근거가 없다.**

## B7. 팀 공유 상태의 동시 편집 — 마지막 저장이 이긴다, 누구인지 안 남는다

- **잠금·버전 검사가 없다.** `patch_row` 는 `user_json` 을 읽어 고쳐 쓴다.
  단일 uvicorn 워커라 쓰기는 직렬화되지만 **나중 것이 앞의 것을 덮는다.**
  두 사람이 같은 칸을 고치면 뒤에 누른 값만 남고, 앞 사람은 알 수 없다.
- **작성자가 없다.** `feedback` 테이블은 편집을 **전부** 남기지만
  (`created_at` · `field` · `ai_value` · `user_value` · `pattern` ·
  근거 스냅숏) 컬럼에 **사람을 가리키는 것이 하나도 없다**:
  `id · job_id · created_at · kind · row_key · page_no · drawing_no ·
  rect_json · field · ai_value · user_value · reason · pattern ·
  basis_json · geometry_json`.
- 화면에도 없다. `td.edited` 는 "고쳐졌다"만 말하고 누가·언제는 말하지 않으며,
  "사람이 고친 값" 줄은 **근거 패널이 아니라 오류 신고 미리보기**에만 있다.

**즉 "누가 고쳤나" 는 지금 어디에도 없다. 이것이 이 회차의 진짜 공백이다.**

## 조사가 잡은 결함 (요구와 별개로 발견)

1. **`cancelled` 가 영어로 나간다** — 첫 화면 목록. `jobLine()` 한 곳.
2. **근거 패널이 편집값과 엔진 근거를 섞어 놓고 구분하지 않는다.**
   실측 캡처(`out/round13/d4_author.png`)에서 한 행이 이렇게 읽힌다:

   ```
   공급 주체    SCT 공급                     ← 편집값
   발주처 양식  나갑니다                      ← 편집값 기준
   적용 규칙    VENDOR_MARK_BOX               ← 엔진 근거
   NOTES 원문   … SUPPLIED BY HRSG            ← 엔진 근거
   수량         7                             ← 편집값
   수량 근거    1 symbol x 2 (…)              ← 엔진 근거 (2)
   ```

   `수량 7` 과 `수량 근거 … x 2` 가 **서로 모순**이다. 12회차가 고친 것과
   같은 종류(화면이 사실과 어긋남)가 **편집 축에 그대로 남아 있다.**
