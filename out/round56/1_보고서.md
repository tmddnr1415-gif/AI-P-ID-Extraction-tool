# 56회차 — 9차 피드백 잔여: p12 별표 · p12 XV · Control Valve 심볼

측정 도구 `spike/` 없이 저장된 결과(`out/regression_3p/TC2.json`)와 렌더로 확인했다.

## 1. p12 의 LIT 가 SCT 인 것은 **도면이 그렇게 말한 것**이다 (결함 아님)

지적: *"Tank 에 LIT 가 `*` 표기가 있음에도 SCT 로 잘못 분류됨"*.

실측 — 두 LIT 행 모두 별표를 **찾았고**(`rules_hit: VENDOR_MARK_GLYPH` ·
`vendor_supply: VENDOR` · `stars: 1`), 그 장 NOTES 가 그 별표를 이렇게 정의한다:

| 표기 | p12 NOTES 정의줄 | SCOPE |
| --- | --- | --- |
| `*`  | **BY SCT** | `SCT` |
| `**` | PUMP SUPPLIER'S SCOPE | `VENDOR(PUMP SUPPLIER'S SCOPE)` |

렌더 `out/tc2_p12/notes_def.png` 가 그 두 줄이고, `lit_wide.png` 가 두 LIT
버블 위의 별표가 **한 개씩**인 것이다.  별표 하나 → `BY SCT` → **SCT**.

이것은 26회차가 세운 규칙 그대로다 — *별표는 "누가 공급하는가" 를 가리키는
것이지 "타사" 를 뜻하지 않는다.*  `VENDOR(SCT)` 로 적으면 **"타사 공급 = 우리"**
가 되고 발주처 양식에서도 빠진다.  같은 장의 `**` 를 단 PI 4행은 정상적으로
`VENDOR(PUMP SUPPLIER'S SCOPE)` 로 나간다 (p12 SCOPE = SCT 15 · VENDOR 4).

**코드를 고치지 않았다.**  고치면 도면이 인쇄한 문장을 뒤집는 것이 된다.

## 2. p12 의 XV 는 **행이 있다** — 다만 검토 탭이다

p12 행 19개의 표기: `PI 4 · PIT 3 · LIT 2 · Analyzer 2 · PDIT 2 · MOV(GLOBE) 2 ·

그 장이 인쇄한 밸브 태그 버블은 `MOV 2 · XV 1` 이고 **행과 정확히 같다.**

## 7. Shift 다중 선택 · 공급 주체 일괄 변경 (요구 — TC2 9차)

`S.sel`(한 행)은 건드리지 않고 `S.multi`(Set)를 따로 뒀다 — 근거 패널 · 배관
추적 · 가운데 맞추기가 전부 한 행을 전제하기 때문이다.  저장하는 길은 **한
행짜리와 같은 PATCH**(`field: "scope"`)이고, 작성자는 **한 번만** 묻고 모든 행에
같이 적는다 (13회차 — 확인은 매번, 타자는 한 번).

**화면 자기검증** (`spike/ui_audit_multiscope.py` · `out/round56/ui/`) — 서버를
띄워 실제로 눌렀다:

| 확인 | 결과 |
| --- | --- |
| 그냥 클릭 | `multi 0` · 한 행 선택 |
| Shift 한 번 → 두 번 | **2 → 3** (첫 Shift 는 이미 고른 행과 둘) |
| 같은 것을 또 누르면 | 3 → **2** → 3 (토글) |
| 패널 | “선택 3개 — 공급 주체를 한 번에” · 짙게 칠해진 상자 **3** |
| 취소 | 값 그대로 `['SCT','SCT','SCT']` — **한 행도 안 고친다** |
| 적용 | 화면·**서버 둘 다** `['VENDOR','VENDOR','VENDOR']` |
| 범례 | SCT **52 → 49** · VENDOR **0 → 3** (33회차 등식 유지) |
| 상자 색 | `#ff9f0a` 셋 (`itemScope` 하나가 정한다) |
| 편집 이력 | `scope:감사` |
| 콘솔 오류 · 실 DB sha256 | 없음 · **불변** |

## 8. DXF 그림 — 옅은 잉크를 읽히는 밝기로 (현장 보고)

*"DXF 의 값, PIT · LIT 등은 진하게 표기해줘, 너무 잘 안 보인다"*.

원인은 검출도 글꼴도 아니라 **그 층의 색**이다.  UAD p6 실측 글자 색:
`#000000` 317 · `#ffff00` 57 · `#00ffff` 46 · `#00ff00` 34 · `#ffff7f` 18 …
노랑·하늘색·연두는 CAD 의 **검은 바탕**에서는 잘 보이지만 흰 종이에서는
거의 사라진다.

**★ 스스로 뒤집은 것** — 엔티티 단계에서 고치려 했다.  `Frontend
.push_property_override_function` 으로 TEXT·MTEXT·ATTRIB 색을 바꿨더니
**호출은 되는데**(TEXT 221 · MTEXT 101 · ATTDEF 135 · ATTRIB 22)
**그려진 글자 색이 한 픽셀도 안 바뀐다** — 일부러 자홍으로 덮어써 확인했다.
그래서 고치는 자리를 **그림**으로 옮겼다 (`dxf_render.darken_ink`):
어느 엔티티 종류든 빠지지 않는다.

규칙은 하나 — **색상은 그대로 두고 밝기만** 문턱(상대휘도 0.42)까지 내린다.
종이(0.96 초과)와 이미 어두운 잉크는 한 칸도 안 움직인다.  층 색으로 읽는
값(파랑 배관 · 자홍 경계)은 살아 있다.

함께 `PX_PER_UNIT` **3.0 → 4.0** (2523 → 3364px) — 사람이 버블 안 글자를
읽으려고 크게 확대하는데 3.0 에서는 한 획이 1px 이라 흐려진다.
⚠ 비용: 장당 **4.0초 → 7.4초**(그리기 4.6 + 밝기 2.8) · PNG 416 → 606KB.
**장마다 한 번 그려 디스크에 캐시**되므로 두 번째부터는 그대로다.

오버레이 음영도 올렸다 — `fill-opacity` **0.13 → 0.20**(고른 것 0.22 → 0.30 ·
묶음 0.40).  DXF 는 층마다 색이 달라 0.13 이 그 색들 사이에서 보이지 않는다.

## 9. Shift + 끌기 = 선택 띠 (요구)

*"마우스 왼쪽 누르고 블록을 지정하면 식별된 계기들이 다 선택될 수 있도록"*.

그냥 끄는 것은 **팬**이고 마크업 모드의 끌기는 **누락 행**이라 둘 다 이미
임자가 있다.  그래서 **Shift + 끌기**로 뒀다 — Shift + 클릭이 "더한다" 인 것과
같은 뜻이고 손가락 하나로 둘을 익힌다.  띠와 **겹치는**(CAD 의 crossing window)
상자 중 **지금 화면에 보이는 것**만 잡는다 (`itemVisible` — 범례에서 꺼 둔 층이
조용히 묶이면 사람이 고른 것과 바뀌는 것이 달라진다).  하나만 잡히면 묶음이
아니라 그 행을 고른 것으로 본다.

실측 (TC2 p22): 화면의 상자 **52개 중 52개**가 묶이고 전부 짙게 칠해지며
패널이 “선택 52개 — 공급 주체를 한 번에”.

## 10. UAD p30 의 `LS` 가 SCT 로 나가던 것 — **별표는 그 심볼의 이름이 아니다**

지적: *"UAD 첨부 장에 있는 LS 도 Vendor 공급 아닌가?"* (p30 `1A5J-00GMA10-M05-0001`).

원인은 DXF 경로가 **심볼 사각형 안에 든 낱말을 별표 후보에서 빼던 장치**
(`_own_words`)다.  그 장치는 *자기 라벨(ISA 글자 · 태그 코드)을 남의 표시로
읽지 않기* 위한 것인데, `stars` 는 `STAR_RE`(`*` · `(*)`)만 담으므로 라벨이
섞일 길이 **애초에 없다**.  그런데 도면은 별표를 **버블 모서리**에 찍고 그
자리는 바깥 사각형 **안**이라(30회차 §10-10 의 **반대 방향**) 진짜 별표를
삼켰다.

실측 (p30): 별표 낱말 60개 · NOTES 정의줄 `* SUPPLIED BY PUMP SUPPLIER`.

| 행 | 겹치는 별표 | 그중 사각형 **안** | 결과(전) |
| --- | ---: | ---: | --- |
| `LS` 12 | 12 | **12** | 전부 SCT |
| `PI` 24 | 24 | 3 | 전부 VENDOR(PUMP SUPPLIER) |

렌더로 확인했다 (`out/round56/dxfrender/p30_LS.png`) — `LS++,+,-,--` /
`00GMA01CL101` 버블의 **오른쪽 위 모서리에 `*`** 가 찍혀 있다.

**결과**: UAD-DXF **행 494 · Q'ty 494 그대로**이고 움직인 칸은
`scope`·`vendor_supply` **13행**뿐이다 (p30 12 · p31 1 · 전부
`LS` SCT → `VENDOR(PUMP SUPPLIER)`).  지문 `a59f9c21` → **`a5d8b79c`**.

## 11. ★ 반투명 음영은 **한 번도 칠해진 적이 없었다** (DXF 빗금을 파다가 드러남)

요구: *"DXF 의 경우 식별 표기를 위해 표기된 네모난 박스 내부에 빗금을 쳐 달라."*

빗금은 SVG `<pattern>` 으로 넣었는데 **한 줄도 안 그려졌다.**  살아 있는 페이지에
같은 패턴을 직접 그려 보니 **멀쩡히 칠해진다** (`out/round56/patprobe/probe.png`
— 솔리드 · 회전 빗금 · 세로 빗금 셋 다).  그래서 원인은 패턴이 아니었다.

**원인: `styles.css` 의 `rect.det { fill: transparent }` 이 이긴다.**
그 줄은 상자 **안쪽까지 클릭이 통하게** 하려고 둔 것인데(주석이 그렇게 적고
있다), CSS 규칙은 **표현 속성**(`setAttribute("fill", …)`)을 언제나 이긴다.
9차 피드백 [3] 의 *"식별된 것은 투명한 음영으로 확실하게"* 는 코드가 도는데도
**화면에 닿은 적이 없었고**, 그래서 사용자가 같은 말을 두 번(*"투명한 음영"* →
*"전체 블럭을 색칠"*) 했다.  나는 그것을 카메라 노출 탓으로 설명하고 있었다.

고침은 한 줄 — **인라인 스타일로 칠한다** (`r.style.fill = …`).  인라인 스타일은
CSS 규칙을 이기고, `fill: transparent` 는 칠하지 않는 것(제외 심볼)의 기본값으로
그대로 남는다.

**따라서 PDF 도 이번에 처음으로 실제로 칠해진다** (`fill-opacity` 0.20).

### 빗금 (DXF 만)

무늬는 색마다 하나씩 그 자리에서 만들고(`hatchFill`), 색은 **테두리와 같은 값**
이다 — 빗금은 무늬이지 색이 아니다.  DXF 만 거는 이유: DXF 는 층마다 색이 달라
평평한 음영이 "덧칠한 색" 과 구별되지 않지만, 빗금은 **도면에 없는 무늬**라
무엇이 우리 표시인지 한눈에 갈린다.  PDF 는 검은 잉크뿐이라 음영으로 충분하다.

실측 (UAD-DXF p18 · 화면 자기검증 `spike/ui_audit_dxf_hatch.py`):
칠한 상자 **50 · 빗금 50** · 무늬 **1개**(쓰인 색 1종) ·
**무늬 색 = 테두리 색** · 콘솔 오류 없음 · 실 DB sha256 불변.

## 12. "빗금이 안 보인다 · Shift 끌기가 안 된다" — 화면 파일이 옛것이었다

두 기능 다 서버 파일에는 들어 있는데 화면에 없었다.  **상자에 음영조차 없었다**
— hotfix9 의 인라인 칠하기가 들어갔으면 PDF·DXF 가릴 것 없이 칠해진다.  즉
브라우저가 **옛 `app.js` 를 캐시로 쓰고 있었다.**

`/static/app.js` 는 늘 같은 주소였고, `Ctrl+Shift+R` 로 풀리지만 **사람이 그걸
기억해야 한다는 것이 결함**이다.  두 번 같은 보고를 받았다.

고친 것 셋:

1. **주소에 내용 딱지를 붙인다** — `GET /` 가 `/static/app.js?v=<sha8>` 로
   바꿔 내보내고 HTML 자체는 `Cache-Control: no-store`.  파일이 바뀌면 주소가
   바뀌므로 캐시가 **구조적으로** 비켜간다.
2. **바닥줄이 지금 받은 화면 파일의 딱지를 적는다** (`v1.0.0 · … · 화면 a1b2c3d4`).
   캡처 한 장으로 *서버 파일이 새것인가* 와 *화면이 그것을 받았는가* 가 갈린다.
3. **띠를 상자 위에서도 연다.**  처음 판은 상자 위에서 시작하면 띠를 안 열었는데
   (그 자리는 상자 자기 클릭이라고 봤다), 붐비는 장에서는 빈 자리를 찾기가 더
   어렵다.  끌지 않았으면(4px 이하) 아무 것도 하지 않으므로 Shift + 클릭(더하기)은
   그대로다.  `pointerdown` 의 `preventDefault` 도 뺐다 — 그것이 클릭을 막았다.

그리고 `isDxfJob()` 이 **두 곳**을 본다 — 분석 기록(`job.input_kind`)과 엔진이
결과에 적은 것(`engine.input_kind`).  옛 분석은 job 열이 비어 있을 수 있다.

## 13. 분석이 느려진 것은 해상도 때문이 아니다

`dxf_render` 를 부르는 곳은 `main._dxf_page_png` **하나**이고 그것은
`GET /jobs/{id}/page/{n}.png` — **화면에 그림을 보낼 때**다.  분석 경로
(`dxf_pipeline.analyse`)는 그 모듈을 import 조차 하지 않는다.  해상도 변경은
**그 장을 처음 볼 때 4.0초 → 7.4초**이고 분석 시간에는 닿지 않는다.

이 환경 실측 (UAD 32장): **`open_set` 63.0초 · 분석 전체 76.1초** —
**83%가 DXF 파일을 여는 단계**다 (ezdxf 파싱).  이번 회차에 `dxf_reader.py` 는
**한 줄도 고치지 않았다** (`git diff --stat` 로 확인).

⚠ 회사 PC 의 3분 40초 → 5분 36초는 이 환경에서 **재현할 수 없다** — 그 자리의
코드가 같으므로 원인은 기계·파일 쪽이다 (다시 올린 `dxf (2).zip` 의 내용 ·
백신 검사 · 다른 부하).  **모른다고 적는다.**
