사용자: *"이전 Rev.A, 현재 Rev.B 나란히 대조 누르면 너무 시간이 오래 걸리고 렉 걸린다.
가볍게 동작할 수 있도록 해결해 줘."*

**엔진 0줄 · 네 프로젝트 기준선 불변** (판정에 닿는 코드가 없다 — 바뀐 것은 `/rows`·`/pages` 의
직렬화 방식, 새 엔드포인트 `/anchors`, 장 그림 디스크 캐시, 읽기 전용 엔드포인트의 행 메모, 화면).
빠른 시험 731 → **742**.

## 1. 어디서 시간이 갔나 — 실측 (QFE Rev.B 2,041행 ↔ Rev.A 1,999행 · 실제 브라우저 · 실제 서버)

### 원인 넷

1. **★ 나란히가 직전 결과의 행 전체를 읽고 있었다.**  hotfix40 이 "수정된 행의 이전 자리(MOD 고리)" 를
   안정 ID 로 찾으려고 `/jobs/{prev}/rows?tab=ALL` 을 통째로 받았다 — QFE 에서 **13.7MB**, 그중 `evidence`
   가 82%(10.9MB).  서버에서 2.5~3.1초(파싱 0.85 + FastAPI 변환기 0.97 + dumps 0.45), 브라우저가 그것을 풀어
   들고 있어 힙 +30MB.  필요한 것은 ID 마다 장·사각형 하나다.
2. **장 그림(PNG)을 요청마다 PDF 를 열어 다시 그렸다** — QFE A1 한 장 0.65~0.96초.  나란히에서는 장을 바꿀
   때마다 **두 장**(왼쪽 현재 + 오른쪽 직전)이라 1.2~1.9초.
3. **전환 때 목록을 두 번 그리고, 그때마다 2,000행 표의 레이아웃을 강제했다.**  (가) `open()` 이 주소를 바꾸면
   `hashchange` 가 "같은 분석 · 다른 필터" 갈래로 들어가 **옛 결과의 행으로** 목록을 한 번 더 그렸다.
   (나) hotfix26 의 머리글 관찰자(`MutationObserver → getBoundingClientRect`)가 머리글이 바뀐 **직후** 재서
   방금 세운 표의 레이아웃을 그 자리에서 강제했다 — CPU 프로파일에서 `getBoundingClientRect` **2,257ms**
   (두 번 · 한 번 0.9초).
4. **한 요청에 행을 다섯 번 파싱했다.**  결과를 열 때 `/review` · `/markup` · `/drawings` · `/multipliers` ·
   `/axis_overrides` 가 저마다 `merged_rows` 를 불러 evidence 10.9MB 를 다시 읽는다 — 각 0.3~0.4초, 직렬 1.75초.
   (`/axis_overrides` 는 **2바이트**를 돌려주는 데 348ms 였다.)

## 2. 고친 것

| 자리 | 전 | 후 |
| --- | --- | --- |
| `GET /jobs/{id}/anchors` (신설) | — | 안정 ID → `{page_no, rect, key}` (`revision_state` ⋈ `item` · 판정 없음 · QFE 178KB) |
| `app.js cmpLoad` | `/jobs/{id}` + `/pages` + `/rows?tab=ALL` | `/pages` + `/anchors` (같은 결과를 두 번 읽지 않는다) |
| `page_png` | 요청마다 렌더 | **디스크 캐시** `page_cache/<job>/p<n>_z<zoom>.png` — 한 번 그리고 둔다 (임시 파일 → `os.replace`) · 분석 삭제 때 같이 지움 · 고아는 위생 감사가 센다 (`orphan_page_cache`) |
| `db.merged_rows_cached` (신설) | 읽기 전용 다섯 곳이 각자 파싱 | 마지막 파싱 목록을 나눠 쓴다.  **도장** = 이 연결의 `total_changes` + `PRAGMA data_version` — 편집 한 칸(이 연결)도, 다른 연결의 커밋도 다시 파싱한다.  둘까지만 든다(분석 하나 약 60MB).  `/rows` 는 열을 더하므로 얕은 복사 |
| `/rows` · `/pages` | FastAPI 변환기 → dumps | `json.dumps` 바로 (내용 같음 · 띄어쓰기만 뺌) |
| `hashchange` | 읽는 중에도 목록을 그림 | `S.loading` 이면 아무것도 안 함 (`open()` 이 끝에 그린다) |
| 머리글 재기 | 머리글이 바뀐 직후 | 한 프레임 뒤(그려진 뒤) · 여러 번 바뀌어도 한 번 |
| `cmpSyncScroll` | 스크롤 이벤트마다 반대쪽에 씀 | **프레임에 한 번** · 값이 같으면 안 씀 |
| `cmpShow` | — | 번호표(`S._cmpSeq`) — 빠르게 넘길 때 앞 장의 읽기가 뒤 장 위에 그려지지 않는다 · `img.decoding = async` |
| `cmpPrefetch` (신설) | — | 1.2초 쉬면 양쪽 결과의 앞·뒤 장 그림을 미리 받는다 (바로 받으면 다음 장 그림과 서버에서 겨룬다 — 실측 1.7 → 3.3초) |

## 4. 남은 것 (이번에 안 한 것)

* 결과를 처음 열 때의 **목록 2,000행 레이아웃(약 0.9초)** 은 남는다 — 표를 가상화하거나 `table-layout: fixed`
  로 바꾸는 일이고(hotfix26 이 "열 폭은 내용이 정한다" 로 둔 자리), 화면 모양이 바뀌므로 묻고 한다.
* 캐시가 빈 첫 장 바꾸기는 여전히 두 장을 그린다(1.1~2.2초) — 그 뒤로는 90ms.  미리 받기는 쉬는 동안 앞·뒤 한 장씩만.
* 축1·축2 · SADARA·UAD PDF · Excel 양식은 이 환경에 없어 못 쟀다 (엔진 0줄이라 지문은 구조적으로 불변).
