# [D] 마크업 제안 속도 — 실측 · 고친 것 · 전후

## 1. 먼저 쟀다 (44회차가 지목한 것이 맞았다)

사각형 하나를 그릴 때마다 `pipeline.propose_at` 이 **PDF 전체를 다시 연다**.

| 프로젝트 | `load_pages` (전 장) | 제안 1회 |
| --- | ---: | ---: |
| AL NOUF1 (58장) | 1.85s | **6.92s** |
| TC2 (60장) | 2.25s | **6.47s** |
| UAD (32장 · SHX) | **8.62s** | **13.75s** |

나머지(4.2~5.1초)는 그 장의 검출 재료 — 버블 윤곽 · 파선 윤곽(40·41회차) ·
마크 사전 · 마크 · 패키지 상자 — 를 매번 새로 만드는 값이다.
**두 번째 제안도 똑같이 걸렸다** (6.54 · 6.18 · 13.70).

## 2. 고친 것 둘 — 값은 그대로 두고 두 번 일하지 않게

1. **그 장만 연다** — `pidcache.load_pages(pdf, only=(n,))`.
   ⚠ **분석 경로는 쓰지 않는다.**  `_scope_by_project` 는 *다수결*이라 한 장만
   넣으면 그 장이 곧 다수가 되어 44회차 [C](남의 프로젝트 장 빼기)가 무력해진다.
   제안은 이미 분석이 받아들인 장 위에서만 도는 일이라 문제가 없고,
   `tests/test_markup_speed.py` 가 `_analyse` 에 `only=` 가 없음을 강제한다.
2. **그 장의 재료를 한 장치 든다** — `_propose_page` (`_PROPOSE_CACHE`).
   키는 (PDF · 장 · config 서명)이고 **한 장만** 든다 — 다음 장을 읽으면 앞
   장이 밀려난다 (33회차 `_INK_LAST` 와 같은 규율).
3. **제안이 끝나면 잉크 인덱스를 놓는다** (`_ProposeCleanup`).  `analyse` 는
   `finally` 에서 놓고 있었는데 제안 경로에는 그것이 없었다.

## 4. 게이트

* **제안 값 불변** — 같은 사각형 두 번이 글자 그대로 같은 dict이고, 다른 장을
  거쳐 캐시가 밀려난 뒤에도 같다 (`test_the_same_rectangle_gives_the_same_answer`).
  44회차 `tests/test_markup.py` 의 값 시험(p6 별표 → `VENDOR(HRSG)`/DRAWING ·
  별표 없는 자리 → 빈칸/USER)도 그대로 통과한다.
* **네 프로젝트 지문**: 분석 경로는 `only=` 도 캐시도 쓰지 않는다 (시험이 강제).
* 빠른 시험 340 → **349**.

## 5. 하지 않은 것

* **화면에서 줄이는 길**(드래그 즉시 빈 행 → 제안 도착 시 채우기 · 연속 마크업
  모드)은 이번에 하지 않았다.  서버가 0.00초로 답하는 구간이 생겼으므로
  체감의 대부분이 사라졌고, 화면 구조를 바꾸는 일은 별도 회차가 맞다.
