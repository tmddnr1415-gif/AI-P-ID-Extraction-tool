## ★ 스스로 뒤집은 판단

1. **첫 축 정의는 엔진이 아니라 채점기를 재고 있었다.**  AL NOUF1 88.8점 · ③ 185/336.
   원인 둘 다 채점기에 있었다 — 도면은 `TT`·`PT`·`LSH` 로 인쇄하고 엔진은
   `anchors.type_map` 으로 `TIT`·`PIT`·`LS` 로 바꿔 행을 내는데 글자 그대로 비교했고,
   `MOV`·`PSV` 를 계기·밸브 양쪽에서 세어 계기 쪽에서 반드시 틀렸다.
   고친 뒤 **88.8 → 94.8**, TC2 도 60.8 → 64.8 로 **같이** 올라 순위와 격차는 그대로다.
2. **UI 실패는 제품이 아니라 데이터였다** (아래).  고친 뒤 **24 전량 통과**.
3. **★ 대기 셸 셋이 8시간 40분 헛돌았다.**  `pgrep -f "pytest -q -m ui"` 가 **자기
   셸의 명령줄**에 걸려(재현: pytest 0개인데 자기 셸 3개가 잡힘) 셋 다 자기 자신을
   기다렸고, 그중 하나는 통과하면 UI 를 띄울 셸이라 **UI 가 시작조차 안 됐는데
   "도는 중" 으로 보고했다.**  판정 근거는 로그 mtime 이었다.  CLAUDE.md §8 에
   규칙 넷을 박았다 — `timeout 900` 상한 · **완료 표식 파일**을 기다림 · `pgrep`
   패턴을 자기 명령줄에 적지 않음 · 상한에 걸리면 실패로 적음.

## ⚠ 이 환경에서 겪은 것 — 그대로 적는다

1. **컨테이너가 한 번 재시작됐다.**  하네스 프로세스가 끊겼지만 세 분석 결과 json 이
   남아 있어 `--reuse` 로 채점만 다시 했다.  **재분석은 하지 않았다.**
2. **★ UI 스위트가 실패했고, 원인은 데이터였다.**  이 PC 의 실 DB 에는 10회차 이전
   분석 넷(824·824·824·75행)뿐이고 **SCOPE 가 전부 빈칸**이다.  20회차가 검증용으로
   만들어 UI 24 를 통과시킨 DB 는 재시작으로 사라졌다.  시험은 14회차 설계대로
   **건너뛰지 않고 실패**했다 (`need five live SCT Field rows · assert 2 == 5`).
   `spike/build_ui_db.py` 로 저장된 결과에서 그 DB 를 다시 세웠다 — **재분석 없이**
   `db.store_result` 로 넣고, `legacy` 갈래를 위해 실 DB 를 읽어 복사한 위에 얹었다.
   ⚠ 처음에는 그 job 의 `pdf_path` 를 비워 둬 재분석 시험(step7)이 실패했고 그것이
   뒤 시험 넷으로 번졌다 — **제품이 아니라 픽스처의 결함**이었고, 넷은 단독으로 통과한다.
3. **메모리.**  TC2 최대 RSS **7.2GB**, AL NOUF1 4.8GB, SADARA 0.8GB.  이 환경에서
   두 분석을 동시에 돌렸을 때 **실제로 OOM 이 났다**.  회사 PC 판단 근거는 아래.

## + 메모리 7.2GB 가 회사 PC 에서 문제가 되는가

- **단독 실행이면 8GB 기계에서도 아슬아슬하게 돈다** — 측정값이 최대 RSS 7.2GB 이고
  운영체제·브라우저가 함께 있으면 스왑을 쓴다.  **16GB 이상을 권한다.**
- **동시 실행은 안 된다.**  이 환경에서 두 분석을 겹쳐 돌리자 7.5GB 에서 OOM 으로
  죽었다.  프로그램은 분석을 하나씩 돌리므로 사용자가 창을 둘 띄우지 않는 한 겹치지 않는다.
- **왜 TC2 가 AL NOUF1 보다 큰가**: 쪽이 60장(58장)이고 장당 도형이 54,436개다.
  `layout` 단계가 전체의 79.7% 를 쓴다.  줄이는 것은 이번 범위 밖이다.
