### ⚠ 발견한 결함 — UI 시험 2건은 **10회차 이전 데이터에서만** 통과한다

고치지 않고 보고한다 (이 작업은 포장과 검증이다).

```
FAILED test_step6_edits_reach_the_excel
FAILED test_step6_scope_edit_removes_the_row_from_the_client_workbook
        AssertionError: SCOPE 를 SCT 아닌 값으로 고쳤는데 행이 그대로다 (667 → 667)
```

**제품 결함이 아니라 시험의 가정이다.**  `edited` 픽스처가 FIELD **첫 다섯 행**을
집어 고치는데, 그 행이 SCT 인지 확인하지 않는다.  11회차부터 발주처 양식은
SCOPE=SCT 만 담으므로, 첫 다섯에 VENDOR 행이 섞이면

- 고친 값이 양식에 안 실린다 → `edits_reach_the_excel` 실패
- 이미 범위 밖인 행의 SCOPE 를 또 바꿔도 행 수가 안 준다 → `scope_edit_removes` 실패

**API 로만 재현해 제품 쪽은 정상임을 확인했다**:
대상 행이 이미 `VENDOR(HRSG)` 였고, 스냅샷은 매번 새로 생겼으며(rev 3 → 4)
`667 / out_of_scope 249` 가 그대로였다 — 필터가 설계대로 동작한 결과다.

**왜 지금까지 통과했나**: 이 스위트는 `app/_data/app.db` 의 사본에서 도는데,
그 DB 의 분석 4건이 **전부 10회차 이전**이다 (824·824·824·75행, SCOPE 전부 빈칸).
빈 SCOPE 는 `legacy` 로 보아 양식에 **담기므로** 다섯 행이 모두 실렸다.
새로 분석한 1029행에서는 FIELD 첫 다섯 중 **3행이 VENDOR(HRSG)** 다.

→ 회사 PC 도 **재분석한 뒤에는** 이 두 시험이 같은 이유로 깨진다.
   `UI 21` 은 그 조건에서 재현되지 않는다.
