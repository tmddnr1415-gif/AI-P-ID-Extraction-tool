## 2. [A-2] 시험이 실 DB 를 여는 길을 끊었다

전문 `docs/round17_test_isolation.md`.

- **닿는 길은 하나였다** — `app/main.py:50` 의 `CON = db.connect(DB_PATH)` 가
  **import 시점에** 돈다.  `from app import main` 하는 시험이 5자리이고 가장
  먼저 도는 하나가 실 DB 를 연다.  `db.connect` 는 읽기 전용이 아니다
  (`journal_mode=WAL` · `executescript(SCHEMA)`).
- **막은 방법은 두 겹이고 둘 다 이미 있는 것을 쓴다**: ① `PID_DATA_DIR`
  (14회차 UI 스위트가 이미 쓰던 변수) 을 버릴 폴더로 · ② 그래도 실
  `app/_data` 밑을 열면 **예외**.  건너뛰지 않고 실패시킨다.
- **읽기는 막지 않는다** — UI 스위트는 실 DB 를 *복사*해 사본에 붙는다.
  막아야 하는 것은 `connect` 이지 `read_bytes` 가 아니다.
- **증명**: 세션 끝에서 실 DB 의 sha256 을 대조한다
  (`pytest_sessionfinish`).  이번 회차 전 시험을 돌린 뒤에도
  `643748dc0efe1681…` 그대로다.

```
12.8 · 18.3 · 18.3 · 18.3 · 18.4 · 18.4 · 18.4 · 18.7 · 18.8 · 19.5 ·
24.6 · 24.7 · 27.1 · 41.4          ← 같은 가장자리 더미.  도면이 안 갈랐다
```

   남긴다 — *"도면에 없는 낱말 — 이 도면 안에서 글자 그대로 같은 문장 N행을
   가르려고 붙인 구분자 (위→아래 · 좌→우 i번째 = X).  테두리 그리드 좌표는
   읽히지 않아 붙이지 않았습니다"*.  근거 패널이 그 글자를 **도면 값과 같은
   얼굴로** 보여 주면 안 된다.
2. 시험은 그 행 자신의 `duplicate_suffix.letter` **한 글자만** 예외로
   허용하고, 예외를 쓴 행에 `SUFFIX:` 사유가 있는지도 **함께** 본다.
   다른 어떤 낱말도 그대로 걸린다.

### ㉡ 그 다음 회차에서 C-4 가 걸렸고, 그것이 진짜 결함이었다

```
FAILED ... AssertionError: axis row eb80c74e0c53ff14 words from no source: {'RETURN'}
```

낱말 자체는 도면에서 왔지만(그 행의 CONNECTOR 후보 문구), **판정축 문형 행**
에서는 `allowed` 를 판정 근거만으로 세우므로 걸렸다.  들여다보니 걸린 것이
**출처가 아니라 판단**이었다 — §4 의 C-4 절에 적은 1195.4 ↔ 1213.7 이 그
행이다.  그래서 시험을 느슨하게 하는 대신 **규칙에 분리 요구치를 넣었고**
(적용 31 → 18), 시험 쪽은 "그 낱말을 말한 CONNECTOR 후보가 실제로 있는가" 를
**확인**하도록 했다 (예외가 아니라 출처 확인이다).

### ㉢ ⚠ 그 시험 수정에서 내가 실수를 하나 냈고 다음 회차가 잡았다

변수 이름을 `dup_letter` → `extra_allowed` 로 일괄 치환하면서 `if dup_letter:`
가 `if extra_allowed:` 가 되어, **접미가 없고 위치어만 있는 행에까지**
"접미 사유가 없다" 를 물었다.  빠른 시험은 전량 분석을 안 하므로 못 잡고
slow 가 잡았다 (`row acea9741daa0f6ba: 접미를 붙였는데 사유가 기록되지
않았다`).  확인을 `dup.get("letter")` 안으로 옮겼다.

**그 뒤로는 11분을 다시 쓰지 않고 저장된 결과로 그 시험만 재생해 확인한다** —
같은 채점 함수를 그대로 부른다 (`replay.py`).

### ⚠ 스스로 찾은 기존 결함 — `dead_ends` 의 순서가 실행마다 다르다

전수 대조 중에 `evidence["trace"]["dead_ends"]` 가 288행에서 달라지는 것을
발견했다.  **같은 코드로 두 번 돌려도 282행이 다르므로 이번 회차와 무관한
기존 비결정성**이다 (`pipe_graph` 의 집합 순회 순서).

```
좌표 집합은 같고 순서만 다르다:
  [[624.7,568.5],[534.2,337.9],[731.3,724.4],[844.4,738.5]]
  [[844.4,738.5],[731.3,724.4],[534.2,337.9],[624.7,568.5]]
```

지문에도, 어느 출력 열에도, Excel(41,466칸 대조 0) 에도 닿지 않고
**근거 패널의 표시 순서만** 흔든다.  고치지 않았다 — 이번 회차의 범위가
아니고, 고치면 그것이 곧 검출 경로를 건드리는 일이다.  **다음 회차 후보로
남긴다.**

### UI 24 는 "SCOPE 있는 데이터" 에서의 값이다 (14회차 그대로)

이 컨테이너의 `app/_data/app.db` 에는 10회차 이전 분석(SCOPE 전부 빈칸)만
들어 있어, 그 DB 로 UI 스위트를 돌리면 **14회차가 심어 둔 전제 시험이
설계대로 실패한다.**

```
FAILED test_step0_the_suite_runs_against_scope_aware_data
  이 DB 에는 SCOPE 가 SCT 가 아닌 FIELD 행이 없다 - 10회차 이전 분석으로 보인다
```

**건너뛰지 않고 실패한다** — 건너뛰기가 세 회차 동안 침묵을 만들었기
때문이다.  이번 회차의 전량 분석 결과(1029행 · SCT 769 / VENDOR 260)를 담은
DB 에서는 **24 전부 통과**한다.  제품의 결함이 아니라 시험이 자기 전제를
말한 것이고, 그것이 14회차가 만든 장치다.

## 7. [E] 기록 삭제 — 분석 단위만 만들었다

전문 `docs/round17_delete.md`, 캡처 `e_delete_list.png`.

**게이트였던 안정 ID 질문의 답**: `Registry.next_seq` 는 `status` 를 **보지
않는다**.  그래서 **분석 하나를 지워도 안정 ID 는 회수되지 않고 재부여되지
않는다** — §7.3 의 "ID 는 Rev.A 에서 한 번만" 이 그대로 지켜진다.

- 지우는 것: `item` · `revision_state` · `deleted_candidate` · `pid_page` ·
  `revision` · `feedback` · `review_state` · `report` 여덟 표의 그 job 행,
  그리고 **다른 분석이 안 쓰는 경우에만** 업로드된 PDF.
- **지우지 않는 것**: `app/_data/projects/…` 의 `id_registry.json`.
  **프로젝트 전체 삭제는 만들지 않았다** — 그 장부가 사라지면 §7.3 이
  실제로 깨진다 (다음 분석이 `10LBA10-001` 을 처음부터 다시 매긴다).
- **누가 언제 무엇을 지웠는지 남는다** (`deletion_log`) — 삭제만 남기고
  내용은 안 남긴다.  `GET /deletions` 로 읽는다.
- 화면은 **미리보기 → 확인 → 분석 ID 를 타자 → 작성자** 네 단계다.
  돌아가는 분석은 거절한다.
