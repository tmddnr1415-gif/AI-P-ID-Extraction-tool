# 산출 시 "도면 근거 없는 값" 자동 점검 — 제안

**제안만 합니다.  구현하지 않았습니다.**

## 왜 필요한가 — 이번에 드러난 것

`field_pid_total.xlsx` 에 UI 시험값이 남아 있었습니다.  그런데 그 사이
`git status` 는 계속 깨끗했습니다.  당연합니다 — `app/_data/` 는 `.gitignore`
대상이고, 값은 **코드가 아니라 스냅샷 DB** 에 있었습니다.

```
$ git check-ignore -v app/_data/app.db
.gitignore:14:app/_data/    app/_data/app.db
```

**"원복했다" 의 확인 방법이 잘못됐습니다.**  확인은 산출물 자체를 열어서 해야
합니다.  이번에는 그렇게 했고, 지적된 2건보다 실제로는 더 많았습니다:

| | 발견 |
| --- | --- |
| 사람이 도면 값을 덮어쓴 칸 | **12** (AL NOUF1 6 + SADARA 6) |
| 도면 근거가 없는 수기 추가 행 | **3** |
| 시험이 지운 행 | **75** |
| 그 상태로 만들어진 스냅샷 | **35** |
| 시험이 쓴 수정이력 | **414** |

행 수로는 FIELD **682행** 이 나오고 있었습니다 (정상 680).  `Q'ty` 도 FIELD
1320 (정상 1301) 이었습니다.  즉 **두 칸이 아니라 표 전체의 수치가 틀려
있었습니다.**  지적된 2건만 지웠다면 여전히 682행이었을 것입니다.

## 무엇을 점검하나

산출물의 모든 값은 셋 중 하나에서 옵니다.  둘은 정당하고 하나는 아닙니다.

| 출처 | 정당한가 |
| --- | --- |
| 엔진이 도면에서 읽음 (`ai_json`) | 예 |
| 검토자가 입력했고 엔진 값이 옆에 남아 있음 (`user_json` + `ai_json`) | 예 — 그러나 **점검 흔적과 구분되지 않으므로 반드시 보여야 함** |
| 어느 쪽도 아님 — 수기로 추가된 행 (`added=1`) | **아니오** |

## 어떻게

산출 직전, 스냅샷의 각 행에서:

```
for 행 in 스냅샷:
    if 행.added:                       -> "도면 근거 없는 행"
    for 필드, 값 in 행.user_json:
        if 값 != 행.ai_json.get(필드):  -> "사람이 도면 값을 덮어쓴 칸"
```

동작 스케치(`/tmp/r6/audit.py` 로 실제 실행해 본 것):

```
=== job fa4ea08c7995   산출 대상 826행
  도면 값을 사람이 덮어쓴 칸 : 6
     p6   FIELD  D00P-10LBA10-M05-0001  type   도면 'TIT' -> 입력 'UI-TYPE-A'
     ...
  도면 근거가 없는 행(수기 추가) : 2
```

정리 뒤 같은 점검:

```
=== job fa4ea08c7995   산출 대상 824행
  도면 값을 사람이 덮어쓴 칸 : 0
  도면 근거가 없는 행(수기 추가) : 0
```

## 어디에 붙이나 — 세 가지 안

| 안 | 동작 | 장단 |
| --- | --- | --- |
| ① 산출물에 리포트 시트 추가 | 덮어쓴 칸·수기 행을 한 시트에 나열 | 산출물이 스스로 증거를 가짐.  다만 발주처 양식에 없는 시트가 늘어남 |
| ② 내려받기 zip 의 MANIFEST 에 기록 | `overridden`, `hand_added` 키 추가 | 양식을 건드리지 않음.  이미 `unmapped_values` 를 그렇게 적고 있음 |
| ③ 화면에서 내려받기 전에 확인 | 0 이 아니면 목록을 보여 주고 진행 여부를 물음 | 사람이 보게 됨.  다만 클릭이 하나 늘어남 |

**②를 권합니다** — MANIFEST 는 이미 있고, 양식을 바꾸지 않으며, 파일을 받은
사람이 나중에도 확인할 수 있습니다.  ③은 ②와 함께 두어도 충돌하지 않습니다.

## 무엇을 막지는 못하나

이 점검은 **덮어쓴 것**과 **추가한 것**을 봅니다.  검토자가 지운 행은 애초에
산출물에 없으므로 이 점검에 걸리지 않습니다.  지운 행까지 보려면 §리비전의
'삭제 후보' 축과 같이 다뤄야 하고, 그것은 별도 회차입니다.

---

# 덧붙임 — 같은 잔존물이 UI 테스트 하나도 통과시키고 있었습니다

DB 를 정리한 뒤 `-m ui` 를 돌리니 `test_step5_survives_row_add_copy_delete` 가
`copy and add did not produce new rows` 로 떨어졌습니다.  조사한 결과 **UI 는
정상이고 테스트가 틀렸습니다.**

`＋행`(`#row-add`)은 행을 만들지 않습니다.  자리 찍기를 **켜기만** 합니다 —
행은 사용자가 도면 위를 클릭하거나 찍기를 취소할 때 만들어집니다
(`app/static/app.js` 의 `#row-add` 핸들러: `clearFiltersForNewRow(); startPick();`).
그러므로 `복사 -> ＋행` 뒤에 늘어나는 행은 **1개**(복사분)뿐입니다.

그런데 테스트는 `len(added) >= 2` 를 봅니다.  DB 에 이전 실행이 남긴
`added=1` 행 2개가 이미 있었으므로, `＋행` 이 아무것도 하지 않아도 조건이
충족됐습니다.  **[0-1] 이 산출물에서 찾은 것과 정확히 같은 덫이 테스트에도
있었습니다** — 잔존물이 초록불을 만들고 있었습니다.

고친 방향: 찍기를 끝까지 진행시키고(`#pick-cancel`), **그 실행이 만든 행만**
세어 `== 2` 를 봅니다.

## 남은 구조적 문제 (제안만)

`tests/test_ui_edits.py` 는 `app/_data/app.db` 를 **그대로 씁니다**
(모듈 docstring: "reuses `app/_data/app.db`, so it does not re-analyse").
그래서 실행할 때마다 편집·추가·삭제·스냅샷이 그 DB 에 쌓입니다.  이번 회차에
지운 것도 그렇게 쌓인 것이고, 방금 실행이 또 쌓았습니다.

제안: 서버 fixture 가 DB 를 **임시 디렉터리로 복사해** 그 사본을 띄우게 합니다
(`PID_DATA_DIR` 같은 환경변수 한 개면 됩니다).  재분석 비용은 그대로 0 이고,
테스트가 원본을 건드리지 않게 됩니다.  구현하지 않았습니다 — 이번 회차의
지시 범위 밖입니다.
