# 21회차 [B] — 어디서 멈추나

원본 예외는 회사 PC 터미널에서 확보됐습니다.  **TC2 파일 자체는 이 작업
환경에 없으므로**(`out/round21_progress.md` §0 — 찾은 자리 전부 기록),
아래는 *예외가 가리킨 자리를 코드와 합성 PDF 로 재현*한 것입니다.
TC2 의 쪽 크기·60장 구성은 파일이 와야 셀 수 있습니다.

## 1. 예외가 가리킨 자리

```
app/pipeline.py:477          library = tb.build_glyph_library(pages, tb.LAYOUT)
extract_titleblocks.py:321   chars = segment_chars(pd.page, clip, lay)
extract_titleblocks.py:248   mask = _ink_mask(page, clip, lay)
extract_titleblocks.py:221   darkest = int(a.min())
ValueError: zero-size array to reduction operation minimum which has no identity
```

`get_pixmap(clip=...)` 은 clip 을 페이지와 **교집합**한 뒤 래스터라이즈합니다.
교집합이 비면 `0 x N` 또는 `N x 0` 픽스맵이 나오고, 그 배열에 `.min()` 을 부르면
위 예외가 납니다.  numpy 의 `min` 은 빈 배열에 항등원이 없어서 정의되지 않습니다.

**스택의 `:321` 은 `build_glyph_library` 의 두 갈래 중 이력 행 갈래입니다.**
(다른 갈래는 `:306`, 텍스트 층이 있는 장의 REV 칸.)

## 2. 0픽셀이 나오는 다섯 모양 — 전부 재현했습니다

`data/` 없이 합성 PDF 로 재현하고 시험에 박았습니다
(`tests/test_titleblock_frame.py::test_a_zero_pixel_clip_returns_none_instead_of_raising`).

| 모양 | 픽스맵 | 고치기 전 |
|---|---|---|
| clip 이 종이 **오른쪽** 밖 (x0 > 쪽 너비) | `0 x 2400` | ValueError |
| clip 이 종이 **아래** 밖 (y0 > 쪽 높이) | `2400 x 0` | ValueError |
| 높이 0 (y0 == y1) | `408 x 0` | ValueError |
| 높이 음수 (y0 > y1) | `408 x 0` | ValueError |
| **이력 행이 `2 x hist_row_inset`(2.4pt) 보다 얇음** | `408 x 0` | ValueError |

마지막 모양이 중요합니다 — **쪽 크기와 무관**하고, 스택이 가리킨 갈래와
정확히 일치합니다.  `build_glyph_library` 는 이력 행 하나마다

```python
clip = pymupdf.Rect(hist_rev_col[0], y0 + hist_row_inset,
                    hist_rev_col[1], y1 - hist_row_inset)
```

를 만드는데, 행 높이가 2.4pt 이하이면 안쪽 여백을 뺀 순간 위아래가 뒤집힙니다.
가로 괘선 두 줄이 가깝게 그려진 양식(겹선·해칭 테두리)에서 그대로 일어납니다.

## 3. 왜 AL NOUF1 에서는 20회차 동안 한 번도 안 보였나

이 문서의 이력 행 **406개(58장)를 전수로 쟀습니다**:

```
min 16.7 · p05 16.7 · 중앙값 16.8 · max 16.8
값은 두 개뿐 — 16.8 이 250개 · 16.7 이 156개
2 x hist_row_inset = 2.4  →  퇴화 행 0개
```

가장 얇은 행이 문턱의 **약 7배**입니다.  이 문서로는 이 갈래에 닿을 수 없습니다.

## 4. `tb.LAYOUT` 은 어디서 오나 — **유도가 아니라 상수입니다**

| 항목 | 답 |
|---|---|
| 자리 | `app/engine/extract_titleblocks.py` `Layout` 데이터클래스 기본값 |
| 덮어쓰기 | 프로젝트 설정 `title_block.` (`_layout_from_config`) |
| 도면에서 유도 | **안 합니다.**  `extract_titleblocks` 에 `derive_*` 함수가 없습니다 |
| 지금 값 | 20개 필드 **전부 기본값** = AL NOUF1 A1 양식에서 잰 값 |

```
dwg_no_region  (1950.0, 1560.0, 2384.0, 1600.0)
title_region   (1960.0, 1500.0, 2384.0, 1574.0)
rev_box        (2296.0, 1583.0, 2326.0, 1597.0)
sheet_box      (2248.0, 1583.0, 2286.0, 1597.0)
hist_rule_y    (1200.0, 1390.0) · hist_rev_col (1971.0, 1988.0)
```

`config/project_alnouf1.yaml` 은 같은 값을 그대로 적어 두었고
(`# measured from this company's A1 form`), `config/project_sadara.yaml` 은
**7개만** 덮어쓰고 `dwg_no_region`·`title_region`·`rev_box`·`sheet_box` 는
AL NOUF1 값을 그대로 물려받습니다.

- AL NOUF1 쪽 크기 **2384 x 1684pt** (58장 전부, A1)
- SADARA 쪽 크기 **3370 x 2384pt** (9장 전부, A0)

SADARA 가 죽지 않는 이유는 양식이 맞아서가 아니라 **종이가 더 커서** clip 이
어쨌든 종이 안에 떨어지기 때문입니다.  종이가 **더 작은** 문서(A3 1191 x 842
등)가 오면 네 칸이 전부 종이 밖이 되고, 그것이 첫 번째 모양입니다.

## 5. 왜 17분이나 걸린 뒤에 실패했나

실패 자리는 `titleblock_glyphs` — **도면을 한 장도 읽기 전**입니다
(`sheets_total` 이 아직 0이라 화면이 장수를 말할 수 없었던 이유이기도 합니다).
그 앞에 서 있는 것이 이 파이프라인에서 가장 긴 두 구간입니다:

**이번 회차 전량 분석의 단계별 실측** (AL NOUF1 58장, 총 441.2초):

| 단계 | 초 | 비중 | 죽은 자리보다 |
|---|---:|---:|---|
| `open_pdf` | 3.14 | 0.7% | 앞 |
| **`layout`** (선분 캐시 예열 + 치수 계산) | **246.79** | **55.9%** | **앞** |
| `titleblock_glyphs` ← **여기서 죽습니다** | 20.50 | 4.6% | — |
| `titleblocks` | 20.78 | 4.7% | 뒤 |
| `legend_rules` | 5.91 | 1.3% | 뒤 |
| 나머지 (밸브 · 계기 · Description …) | 144.1 | 32.7% | 뒤 |

즉 **죽는 자리에 닿기까지 249.9초(4분 10초)가 이미 지나갑니다** — 그중 55.9%
가 `layout` 한 단계입니다 (12회차가 선분 캐시 95.8초 · 치수 계산 129.0초로
쪼개 잰 그 구간).  60장짜리에 사무실 PC 라면 17분은 이 구간과
`build_glyph_library` 가 60장을 다시 훑는 시간으로 설명됩니다.

**17분은 "오래 분석하다 실패한 것"이 아니라 "분석을 시작도 못 한 채 준비
작업만 하다 죽은 것"입니다.**  화면이 장수를 말하지 못한 것도 같은 이유입니다
— `sheets_total` 은 `targets` 가 정해지는 순간(죽은 자리보다 **뒤**)에야 실립니다.

## 6. ⚠ 같이 발견한 것 — 이력 행 캐시가 문서 사이로 샜습니다

`history_rows` 의 캐시가 모듈 전역 dict 였고 키가 **`page_no` 하나**,
지우는 곳이 없었습니다.  서버 프로세스가 살아 있는 동안 **두 번째 문서가 첫
번째 문서의 이력 행을 그대로 물려받습니다.**

실측 (같은 프로세스):

```
SADARA 9장을 혼자 읽으면        →  9장 전부 이력 행 0행
AL NOUF1 을 먼저 읽고 나서 읽으면 →  9장 전부 AL NOUF1 의 7행
                                     [(1358.0, 1374.8), (1341.3, 1358.0), ...]
9장 중 9장이 다릅니다.
```

죽지 않고 값만 틀리는 **조용한 폴백**입니다 (15회차 [B]2 의
`unit_multipliers` 와 같은 모양).  실무에서 이것이 뜻하는 바:

> 새 프로젝트 PDF 의 결과가 **"그 전에 무엇을 분석했느냐"에 따라 달라집니다.**
> 서버를 새로 켜고 TC2 를 먼저 올리면 자기 이력 행을 읽고(퇴화 행이면 죽고),
> AL NOUF1 을 먼저 분석한 뒤 올리면 AL NOUF1 의 16.7pt 행을 받아 **죽지 않는
> 대신 엉뚱한 자리를 읽습니다.**  사용자에게는 같은 파일이 어떤 때는 죽고
> 어떤 때는 안 죽는 것으로 보입니다.

**이것은 보고된 실패의 원인이 아닙니다** — 그 실패는 죽는 쪽이고, 이 캐시는
죽지 않는 쪽을 만듭니다.  다만 같은 자리에서 나온 별개의 결함이고, 재현이
끝났으므로 이번에 고쳤습니다 (§5 대책 3).
