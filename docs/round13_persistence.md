## 1. 첫 화면 — 단위를 job 에서 프로젝트로 (C)

**전**: `이전 분석` 목록이 job 단위였고 PDF 파일명·상태·장수·소요시간만 말했다.
같은 `pid_total.pdf` 로 올린 두 분석을 **구분할 수 없었다.**

**후**: `GET /home` 하나가 프로젝트와 그 리비전을 함께 준다.

```
저장된 프로젝트 — 눌러서 다시 엽니다 (재분석하지 않습니다)
▾ E2E13                                         2개 리비전 · 최신 Rev.B
   Rev.B  도면 Rev.D  (같은 개정)   완료 · 1029행 · 58장 · 2026-09-05 00:00 · 수정 5칸
   Rev.A  도면 Rev.D                완료 · 1029행 · 58장 · 2026-09-04 23:54 · 수정 5칸
```

- 정렬은 **최근순**(프로젝트도, 그 안의 리비전도).  여러 사람이 만든 것이 섞이므로
  마지막에 만진 것이 위에 온다.
- 프로젝트에 안 묶인 분석은 **버리지 않고 따로 묶는다** — "프로젝트 없이 한 번만
  분석" 은 지금도 있는 선택지이고, 그렇게 만든 결과가 목록에서 사라지면 안 된다.
- **`cancelled` 가 영어로 나가던 것을 고쳤다** (조사가 잡은 결함).  `jobLine` 의
  한국어 표에 `cancelled`·`running`·`queued` 가 빠져 있었다.

**실측 (클릭 → 1029행이 화면에 뜨기까지)**

| | |
| --- | ---: |
| `GET /jobs` | 0.002초 |
| `GET /jobs/{id}/rows?tab=ALL` (1029행 · 4.8MB) | 0.69 ~ 0.75초 |
| 브라우저 클릭 → 첫 행 렌더 | **1.5 ~ 2.6초** |
| (대조) 전량 재분석 | **351초** |

**같은 이름 프로젝트**: 서버는 예전부터 409 로 거절해 왔고(덮어쓰지 않는 것이
맞다) 그대로 뒀다.  달라진 것은 **[만들기] 를 누르기 전에** 알린다는 것과,
대개 하려던 일인 "그 프로젝트에 개정본으로 추가" 버튼을 같이 준다는 것이다.
§7.3 의 안정 ID 계보가 프로젝트 단위 약속이므로, 같은 도면을 새 이름으로 또
올리면 계보가 갈라진다.

## 2. 편집 — Rev 사이로 잇는다 (D)

**두 층은 이미 있었다** (`item.ai_json` / `item.user_json`).  없던 것은 그 층이
**리비전을 건너지 못한다**는 것이었다: `user_json` 은 `(job_id, key)` 에 매여
있고, 넘어가는 것은 `axis_overrides` 를 통한 Description 하나뿐이었다.

**짝은 안정 ID 로 짓는다** — 좌표도 행 키도 아니다.  §7.3 이 ID 를 "Rev.A 에서
한 번만 부여하고 재정렬하지 않는" 것으로 정의해 둔 이유가 그것이고, 여기서는
그 ID 를 **쓰는** 것이지 새로 매기지 않는다.

세 가지를 지킨다:

1. **추출값(`ai_json`)은 건드리지 않는다.**  지문·축1·축2·Q'ty 축이 그 층만
   읽으므로 승계가 측정에 새지 않는다.
2. **이번 리비전에서 사람이 이미 고친 칸은 덮지 않는다.**  승계는 빈 자리를
   채우는 것이다.
3. **이어받은 칸을 이번 도면이 다르게 읽었으면 고르지 않는다.**  `conflict_json`
   에 `was_ai`/`now_ai`/`user` 셋을 남기고 검토로 올린다 — 재분석이 하던 것과
   같은 규칙이고, 다른 것은 비교 상대뿐이다.

**실측 (Rev.A 에서 5칸 편집 → Rev.B 분석)**

```
carried  {"from": "Rev.A", "matched": 1, "filled": 5, "conflicts": 0}
Rev.B 의 그 행: description · scope · qty · tag_no · remark 5칸이 그대로
Rev.B 전체 편집 칸: 5  (승계된 것만 있고 다른 행은 건드리지 않았다)
```

### 작성자 — 없던 것을 넣었다

조사에서 `feedback` 15개 컬럼에 **사람을 가리키는 것이 하나도 없었다.**
인증을 만들 자리가 아니므로 자기신고로 하고, 사용자가 "매 편집마다 이름 확인"
을 택했다.  **확인은 매번 하고 타자는 한 번만** 친다 — 지난 이름이 채워진 채로
뜨고 Enter 로 넘어간다.  비우면 비운 채로 저장되고 화면이 "이름 없음" 이라고
적는다.  **서버도 화면도 이름을 지어내지 않는다.**

근거 패널이 "누가 · 언제 · 무엇에서 무엇으로" 를 적는다:

```
수정 이력 6건 — 이름은 자칭입니다 (이 앱에는 로그인이 없습니다)
  김검토   2026-09-05 00:05   remark : 타사 공급 — Description 생략 → 13회차 캡처
  홍길동   2026-09-05 00:05   tag_no : (비어 있음) → T-13 — Rev.A 에서 이어받음
```

### ⚠ 캡처가 잡은 결함 둘

1. **승계된 편집이 이력에 안 남았다.**  Rev.B 의 행은 ✎ 로 "사람이 고쳤다" 고
   말하면서 **누가 언제 고쳤는지는 말하지 못했다** — 화면이 아는 것보다 적게
   말하는 것이고, 팀 공유 중에는 되짚을 수 없다는 뜻이다.  원래 고친 사람의
   이름을 그대로 잇고 사유에 `Rev.A 에서 이어받음` 을 적는다.  지어내는 값이
   없다 — 이름도 값도 이전 리비전의 것 그대로다.
2. **근거 패널이 편집값과 엔진 근거를 섞어 놓고 구분하지 않았다** (조사에서
   발견, 여기서 수정).  한 행이 이렇게 읽혔다:

   ```
   수량        7           ← 편집값
   수량 근거   1 symbol x 2 ← 엔진 근거
   ```

   이제 `수량  9 ✎ 사람이 고침 (도면 근거는 2)` 로 **어디서 온 값인지**를 붙인다.
   값을 바꾸지 않는다.  12회차가 스코프 축에서 고친 것과 같은 종류다.

### ⚠ 문서 대표 Rev 는 도면에서 유도되지 않는다

세 후보가 서로 다른 답을 낸다:

| 규칙 | AL NOUF1 의 답 |
| --- | --- |
| `max` 사전순 최댓값 | **D** (1장) |
| `mode` 최빈값 | **B** (19장) |
| `first_sheet` 1쪽 도면목록 | **B** |

`rev_date` 는 9장에만 있고 가장 늦은 24.NOV.2025 에 C 3장·D 1장이 섞여
갈라지지 않는다.  **즉 도면이 답을 주지 않는다.**  그래서 사용자가 실무
기준으로 **`max`("한 장이라도 개정되면 문서가 개정된 것")** 를 확정했고,
config `revision.document_rule` 한 줄로 갈아 끼운다.  코드에 박지 않았다.

**대표값만 화면에 내지 않는다.**  접기 전 분포와 장 단위 대조를 함께 보인다 —
그쪽에는 임의값이 없다.

### ⚠ 캡처가 잡은 셋째 결함 — 도면번호가 장을 유일하게 가리키지 않는다

같은 PDF 를 두 번 넣었는데 장 단위 대조가 **"개정 2장 · 역행 1장"** 을 냈다.
쪽 단위로 재보니 **rev 판독은 완전히 결정적이었다 (58쪽 중 다른 쪽 0).**
원인은 대조 함수였다: 이 문서에는 **같은 도면번호를 쓰는 PID 장이 3쌍** 있고
그 장들의 개정이 서로 다르다.

```
D00P-10LBG10-M05-0001   p12 B  ↔  p15 A
D00P-00GHC10-M05-0001   p46 C  ↔  p47 B
D00P-00GMA10-M05-0001   p52 A  ↔  p55 B
```

한쪽을 골라 비교하면 같은 문서가 개정으로 읽힌다.  그래서 **그런 도면번호는
판정하지 않고 `ambiguous` 로 센다.**  어느 장이 어느 장의 후속인지는 도면번호로
알 수 없고, 짝을 지어 주는 규칙을 만들면 그것이 곧 임의값이다 (§2.1 ③).
쪽 번호로 짝을 짓는 것도 안 된다 — 개정 때 장 순서가 바뀌는 것이 개정의 흔한
모습이다.

고친 뒤 같은 PDF 두 번의 결과:

```
개정 0 · 그대로 47 · 역행 0 · 신규 0 · 3개 도면번호는 장이 여럿이라 판정 안 함
```

### 판정은 넷뿐이고 추정하지 않는다

`NEWER` 개정본 · `SAME` 같은 개정 · `OLDER` 이전 개정 · `UNKNOWN` 판별 불가.
형식이 `^[A-Z][0-9]?$` 라 사전순이 곧 개정순이다 (A < A1 < B < C < D).
형식이 다른 문서에서는 정렬을 다시 정해야 하고, 그 사실이 코드 주석에 있다.

**범위 밖**: §7.3 의 비교 로직(안정 ID 매칭 · 삭제 후보 · 3색 표시)은 손대지
않았다.  이번에는 **구분해서 보여주는 것까지**다.

## 5. 무엇을 안 했나

- **Rev 간 비교 방식** — 사용자가 "추후 다룬다" 로 명시.
- **동시 편집 충돌** — 여전히 마지막 저장이 이긴다.  잠금도 버전 검사도 넣지
  않았다.  달라진 것은 **누가 덮었는지 이력에 남는다**는 것뿐이고, 그것이
  이번 회차의 범위였다.
- **`app/_data/` 밖 저장** — 편집은 예전과 같은 `item.user_json` 에 있고 새
  저장소를 만들지 않았다.  `axis_overrides.json` 도 그대로 프로젝트 폴더에 있다.
