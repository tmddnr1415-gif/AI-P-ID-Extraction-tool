# 리비전 관리 — 확정 사항과 구현

확정 사항은 실사용자가 정한 것이고, 그 아래 §구현 은 이번 회차에 실제로
만든 것이다.  만들지 않은 것은 §미구현 에 그대로 적어 두었고, 지어내지 않았다.

## 1. 삭제된 행은 자리를 지킨다

삭제 행은 **원래 행 위치**에 남고 **원래 NO** 를 유지한다.  표 끝으로 모으지
않는다.

근거: 발주처가 준 리스트 자체가 그렇게 되어 있다.  `CZE_Field_Instrument.xlsx`
의 취소선 16행은 표 끝이 아니라 원래 자리(144·145·147·156·308·335·336·
513~515·540~544·550)에 있고 NO 도 그대로다.  즉 이 규칙은 우리가 정한 것이
아니라 **발주처 문서에서 읽은 것**이다.

## 2. NO 는 마지막 + 1, 단조 증가, 회수 없음

새 행의 NO 는 항상 그 시점 최대 NO + 1 이다.  삭제된 행의 NO 를 다시 쓰지
않는다.  한 번 나간 NO 는 그 행의 이름이고, 다른 행에 넘기지 않는다.

따라서 NO 는 행 순서와 일치하지 않을 수 있다.  그것이 정상이다 — 순서는 표가
말하고, NO 는 이력이 말한다.

## 3. 무엇과 무엇을 비교하는가

| 리비전 | 기본 비교 대상 | 사용자가 바꿀 수 있나 |
| --- | --- | --- |
| Rev.B | Rev.A | 아니오 (직전이 하나뿐) |
| Rev.C | 직전(Rev.B) | 예 |
| Rev.D 이상 | 직전 | 예 — 이전 리비전 중 아무거나 |

비교 대상은 **화면과 산출물 양쪽에 기록**한다.  표기는 `"Rev.C vs Rev.A"`
형태로 쓰고, 기본값을 쓴 경우에도 생략하지 않는다.  무엇과 비교했는지 적히지
않은 증감표는 읽는 사람이 검증할 수 없다.

## 4. 프로젝트 저장 위치

사용자 PC 의 앱 데이터 디렉터리에 저장한다.  폐쇄망 환경이며 **외부 저장소는
금지**한다.  현재 코드가 이미 그렇게 되어 있다 — `app/paths.py` 가 읽는 뿌리
(번들 안, 종료 시 삭제)와 쓰는 뿌리(exe 옆 `pid_data/`)를 가르고 있고, 네트워크
경로는 어디에도 없다.

## 5. 색

| 상태 | 표시 |
| --- | --- |
| 추가 | 노랑 |
| 삭제 | 붉은 취소선 |
| 수정 | 연녹 |
| Rev.A | 표기 없음 |

Rev.A 는 비교 대상이 없으므로 **음영도 취소선도 하나도 없어야 한다.**
(이 조건은 이미 회귀 항목으로 확인하고 있다 — 산출물 데이터 영역의 음영 0칸 ·
취소선 0칸.)

## 6. P&ID 오버레이에는 추가·수정만

도면 위 오버레이는 **추가**와 **수정**만 그린다.  삭제는 그리지 않는다 —
없어진 심볼을 도면 위에 그릴 자리가 없고, 그리면 있는 것처럼 보인다.
삭제는 표에서만 (붉은 취소선으로) 보인다.

## 7. 삭제는 사람이 확정한다

엔진은 삭제를 **'삭제 후보'** 로 올리기만 하고, 실제 삭제 확정은 사용자가 한다.

이유는 이 문서에서 이미 측정된 것과 같다: 검출이 한 회차에서 사라지는 원인은
"도면에서 없어졌다" 만이 아니라 "이번에 못 찾았다" 도 있다.  전자와 후자를
기계가 가르지 못하므로, 가르는 일을 사람에게 넘긴다.  근거 패널에는 직전
리비전에서의 위치와 그때의 판정 근거를 함께 띄운다.

## 확정 당시 정해지지 않았던 것 — 그 뒤 어떻게 됐나

- ~~같은 행인지 다른 행인지를 무엇으로 판정할 것인가~~ → **정해졌다.**  엔진의
  행 키는 좌표를 포함해 심볼이 조금만 움직여도 바뀌므로 쓰지 않는다.  대신
  안정 ID 를 따로 발급하고, 같은 도면·같은 TYPE 안에서 도면이 정한 반경으로
  맞춘다.  아래 §구현 참조.
- 한 리비전 안에서 사용자가 손으로 넣은 값이 다음 리비전으로 따라가는가 —
  **아직 미정.**  현재는 각 분석이 자기 `user_json` 을 갖고, 리비전 사이로
  옮기지 않는다.
- 증감표를 산출물의 어느 시트에 어떤 형태로 넣는가 — **아직 미정.**

# 구현 (2026-08 회차)

## 안정 ID

```
{KKS 계통코드}-{3자리 순번}      10LBA10-001 · 00PAB10-014
```

계통코드는 도면번호의 두 번째 하이픈 구획에서 나온다
(`D00P-10LBA10-M05-0001` → `10LBA10`).  떼지 못하면 도면번호 전체를 쓰고 그
사실을 레지스트리에 적는다 — 조용히 실패하지 않는다.

SYSTEM 명(`Circulating Water System`)은 쓰지 않는다.  한 계통이 여러 장에
걸쳐 있어 순번이 충돌한다.

**부여는 Rev.A 에서 한 번뿐이다.**  이후 리비전에서 재부여·재정렬하지 않는다.
새 항목은 그 계통의 **최대 순번 + 1**, 삭제가 나도 번호를 회수하지 않는다.
좌표순으로 매번 다시 매기면 도면 가운데에 계기 하나가 들어올 때 뒤 번호가 전부
밀려, 실제로는 1건 추가인데 대조가 "1건 추가 + 40건 수정" 으로 나온다.

**정렬 키** (`revisions.sort_key`): `(round(y), round(x), TYPE, 행 키)`.
부동소수 좌표를 그대로 비교하면 같은 입력에서도 순서가 흔들릴 수 있으므로 1pt
격자로 반올림한다.  실측: 같은 PDF 로 두 번 부여해 `id_registry.json` 의 `ids`
가 **동일**.

**Excel NO 도 같은 원리다** (`revisions.assign_excel_numbers`).  산출물 단위로
매기고, 한 번 받은 번호는 그 행의 이름이다.  Rev.A 에서는 기존 산출 순서
(`system → page_no → key`) 그대로 1..N 을 주므로, 리비전을 쓰기 전과 쓴 뒤의
Rev.A 산출물이 같은 순서·같은 번호를 갖는다.

## 저장소

```
{PID_DATA_DIR 또는 exe 옆 pid_data}/projects/{프로젝트명}/
    project.json        리비전 목록 · 비교 대상 · 상태 수 · 삭제 후보
    id_registry.json    ID 장부
```

`app/paths.py` 의 쓰는 뿌리를 그대로 쓴다 — exe 로 돌 때 **exe 옆 `pid_data/`**
이지 설치 디렉터리가 아니다.  Program Files 밑이면 쓰기가 막히므로 그렇게 갈라
둔 것이고, 프로젝트 저장도 같은 규칙을 따른다.  네트워크 경로는 없다.
두 파일 다 `sort_keys=True` 로 쓰므로 두 번 저장하면 같은 파일이다.

## 매칭과 판정

같은 도면 안에서만, TYPE 이 같은 것끼리만 후보를 만든다.  상호 최근접인 짝을
먼저 확정하고 남은 것을 거리순으로 붙여 1:1 을 보장한다.

**반경은 그 도면 자신의 버블 크기다** (`match_radius`).  버블 사각형은 범례에서
캡 모양(`cap_ratio`)과 옆면(`side_slack`) 짝짓기를 통과한 것만 남은 것이므로(크기 창 `cap_span` 은 37회차에 지웠다), 그
긴변은 이 문서가 정한 심볼 치수다.  코드에 상수가 없고, 도면마다 다시 잰다 —
실측하면 이 문서 안에서도 54.4 / 68.0 / 85.0 / 85.1pt 로 갈린다.  버블 사각형이
없는 도면에서는 같은 TYPE 최근접 거리의 절반을 쓴다.

| 결과 | 상태 |
| --- | --- |
| 짝을 찾음 · 값 같음 | `UNCHANGED` |
| 짝을 찾음 · 값 다름 | `MODIFIED` (어느 칸이 어떻게 바뀌었는지 전부 기록) |
| 이번에만 있음 | `ADDED` |
| 직전 ID 가 안 물림 | `DELETED_CANDIDATE` |
| 비교 대상 없음 (Rev.A) | `BASELINE` — 어디에도 표기가 붙지 않는다 |

**자리를 옮긴 것만으로는 '수정' 이 아니다.**  얼마를 움직여야 수정인지에 근거가
없고 어떤 값을 골라도 임의값이며(§2.3), 검토자가 보는 것은 좌표가 아니라 칸의
값이다.  시트를 다시 그린 개정에서 전 행이 '수정' 으로 물드는 쪽이 더 나쁘다.
움직인 거리는 `moved_pt` 로 이력과 상태에 **기록만** 하고 근거 패널에서 보인다.
이 판단은 뒤집을 수 있게 `revisions.compare` 한 곳에 모여 있다.

**삭제는 자동 확정하지 않는다.**  검출 실패와 실제 삭제를 기계가 가르지 못한다.
근거 셋(직전 좌표 · 매칭 반경 · 가장 가까웠던 같은 TYPE 후보까지 거리)을 붙여
사람에게 올리고, 확정 전에는 산출물에 나가지 않는다.

## 색과 형태

| 상태 | 리스트 | P&ID | Excel |
| --- | --- | --- | --- |
| 추가 | 노랑 음영 + 왼쪽 띠 + `＋` | 테두리 3px · 파선 6-3 | 노랑 음영 |
| 수정 | 연녹 음영 + 왼쪽 띠 + `≠` | 테두리 3px · 파선 2-3 | 연녹 음영 |
| 삭제 | 붉은 음영 + 취소선 + `－` | **그리지 않음** (좌표가 없다) | 붉은 음영 + 취소선 |
| 변경없음 / Rev.A | 표기 없음 | 기존 그대로 | 표기 없음 |

도면에서는 **색이 아니라 형태가 말한다** — scope 색(#0a84ff 포함 · #ff9f0a 벤더
제외)을 그대로 두고 테두리 굵기와 파선으로 구분한다.  두 축이 같은 테두리 색을
두고 다투면 어느 쪽도 읽히지 않기 때문이다.  리스트도 색만으로 구분하지 않는다:
왼쪽 굵은 띠와 NO 앞 기호가 색을 빼도 남는다.

## 미구현

- **실제 Rev.A ↔ Rev.B 대조 정확도** — 개정 도면이 없다.  이번 회차의 Rev.B·C 는
  **합성**이다 (Rev.A 결과의 몇 행을 지우고·바꾸고·옮기고·더한 것).
- **매칭 파라미터 튜닝** — 실물 없이 맞출 수 없다.  반경이 도면 버블 긴변
  (85pt) 이고 같은 TYPE 최근접이 18pt 인 도면이 있다.  상호 최근접 + 1:1 로
  뒤바뀜은 막았지만, 실제 개정에서 이 여유가 적절한지는 **미측정**이다.
- **삭제 확정의 되돌림 이력** — 확정/취소는 되지만 누가 언제 했는지는 남기지
  않는다.
- **프로젝트 삭제·이름 변경** — 만들기와 고르기만 있다.
- **한 프로젝트에 도면 세트가 여러 개일 때** — 아래 §확인 대기.

## 확인 대기 (후보만 냅니다)

1. **발주처 개정 표기 색 규칙**  우리는 추가 노랑 · 삭제 붉은 취소선 · 수정
   연녹을 씁니다.  발주처가 쓰는 규칙이 따로 있으면 그쪽에 맞추는 편이
   안전합니다.  색 상수는 `excel_out.REVISION_FILL` · `styles.css` 두 곳에만
   있습니다.
2. **프로젝트명 규칙**  지금은 자유 입력입니다.  후보 셋 — (가) 자유 입력
   (지금), (나) 도면의 프로젝트 코드(`D00P` · `1A46`)를 타이틀블록에서 읽어
   제안하고 고칠 수 있게, (다) 코드로 고정.  (나) 를 권합니다: 코드는 이미
   타이틀블록에서 유도하고 있고(`_document_code`), 프로젝트가 늘었을 때 같은
   이름이 겹치는 일이 줄어듭니다.
3. **한 프로젝트에 도면 세트가 여러 개일 때**  후보 둘 — (가) 세트마다 별도
   프로젝트, (나) 한 프로젝트 안에 세트 축을 두고 ID 를 세트별로 발급.  ID 가
   도면번호에서 나오므로 세트가 달라도 도면번호가 다르면 충돌하지 않습니다.
   그래서 **(가) 로 충분해 보입니다** — 다만 같은 도면번호를 쓰는 두 세트가
   실제로 있는지는 확인이 필요합니다.

# 매칭 반경 — 대안 후보 (기록만, 구현하지 않음)

실제 개정 도면이 없는 상태에서 반경을 튜닝하는 것은 금지 사항입니다.  개정 도면이
오면 바로 시험할 수 있게 후보만 적어 둡니다.  **아래 수치는 전부 이 문서
(AL NOUF1 58장 · 824행) 로 실제로 잰 값**이고, 잴 수 없는 것은 "실물 필요" 라고
적었습니다.  추정치는 쓰지 않았습니다.

## 왜 후보가 필요한가 — 현행의 실측

| 값 | 실측 |
| --- | --- |
| 반경 안에 같은 TYPE 후보가 2개 이상인 앵커 | **169 / 824 = 20.5%** |
| 후보가 항상 1개뿐인 도면 | 42장 중 **20장** |
| 가장 심한 도면 `00GHC10` | 반경 **85.0** ↔ 같은 TYPE 최근접 **18.06** · 54개 중 **37개**가 2개 이상 · 최대 4 |

반경이 계기 간격보다 4.7배 큽니다.  상호최근접 규칙이 그 안에서 짝을 지키고
있지만, 여러 개가 **같이** 움직이면 규칙이 무너집니다.

## 후보 네 가지

### 후보 A — 현행: 그 도면 버블 긴변의 중앙값

| 잰 것 | 값 |
| --- | --- |
| 후보 2개 이상인 앵커 | 20.5% |
| 5개 동시 대각 이동에서 짝이 유지되는 한계 | **42.4pt 까지 유지 · 56.6pt 에서 2건 엇갈림** |
| 113.1pt | 5건 전부 엇갈림 |

엇갈릴 때마다 허위 추가 1 + 허위 삭제후보 1 이 같이 나옵니다.

### 후보 B — `min(버블 긴변, 같은 TYPE 최근접 / 2)`

| 잰 것 | 값 |
| --- | --- |
| 후보 2개 이상인 앵커 | **0 / 824 = 0.0%** |
| 1개만 움직일 때 짝이 유지되는 한계 | **8.5pt 까지 · 14.1pt 에서 놓침** |
| 5개 동시 이동 | 같음 — 8.5pt 까지, 14.1pt 에서 5건 전부 놓침 |

**모호함은 사라지고 관용도가 42.4pt → 8.5pt 로 줄어듭니다.**  도면을 다시 그리면서
심볼이 조금씩 밀린 개정에서는 전부 "추가 + 삭제후보" 로 나옵니다.
(측정은 원숭이패치로 했고 코드는 바꾸지 않았습니다.)

### 후보 C — 반경은 현행대로 두되, 후보가 2개 이상이면 좌표 외의 축으로 한 번 더 가른다

후보가 2개 이상인 **169개 앵커**에서 각 축이 실제로 후보를 가를 수 있는지:

| 축 | 전부 다름 | 일부 다름 | 전부 같음 |
