# DB 위생 — 방침 후보

**후보만 적습니다.  구현하지 않았습니다.  정책은 사용자가 정합니다.**

## 1. 무엇이 쌓였나 — 실측

이번 회차에 손으로 치운 것:

| 항목 | 수 | 크기 |
| --- | ---: | ---: |
| 대응 revision 이 없는 출력 디렉터리 (`_data/outputs/revN`) | **43** | — |
| 어떤 job 도 참조하지 않는 업로드 PDF | **3** | 약 20 MB |
| 시험용 실패 job (빈 PDF) | 1 | — |
| VACUUM 전 `app.db` | | **168 MB** |
| VACUUM 후 `app.db` | | **15 MB** |

**DB 의 91% 가 죽은 페이지였습니다.**  sqlite 는 DELETE 로 파일을 줄이지
않으므로, 회차마다 지운 스냅샷·수정이력이 파일 안에 그대로 남아 있었습니다.

쌓인 경로는 셋입니다.

1. **스냅샷** — 산출물을 만들 때마다 `revision` 행 하나와 `outputs/revN/`
   디렉터리 하나가 생깁니다.  지우는 쪽은 어디에도 없습니다.
2. **업로드** — job 을 지워도 `uploads/` 의 PDF 는 남습니다.  한 건이 20 MB 입니다.
3. **DB 내부** — DELETE 후 VACUUM 이 없으면 파일 크기는 그대로입니다.

## 2. 후보

### (가) 감사기 정기 실행 — 지우지 않고 세기만 한다

이미 있는 두 판독기를 붙여 한 번에 세게 합니다
(`/tmp/r6/audit.py` 가 회차마다 하던 일).  보는 것:

| 볼 것 | 근거 |
| --- | --- |
| 사람이 도면 값을 덮어쓴 칸 | `user_json` ≠ `ai_json` |
| 도면 근거 없는 행 | `added=1` |
| 대응 job 이 없는 업로드 | `uploads/` ∖ `job.pdf_path` |
| 대응 revision 이 없는 출력 디렉터리 | `outputs/revN` ∖ `revision.id` |
| DB 파일 크기 대비 실사용 | `PRAGMA page_count` × `page_size` vs `freelist_count` |

**언제**: 세 시점이 후보입니다.
- **서버 기동 시 1회** — 화면 어딘가에 "정리 가능 N MB" 한 줄.  사용자가 늘 보게 됨
- **산출물 내보내기 직전** — 이미 [0-1] 에서 제안한 MANIFEST 점검과 같은 자리
- **테스트 세션 끝** — 이미 있습니다 (`test_zzz_the_suite_left_the_real_database_alone`)

**장점**: 아무것도 지우지 않으므로 잘못 지울 일이 없습니다.
**단점**: 세기만 하면 쌓이는 것은 그대로입니다.  이번에 43개가 쌓인 것도
"보이지 않아서" 가 아니라 "치울 사람이 없어서" 였습니다.

### (나) 자동 정리 — 지울 수 있는 것만

**지울 수 있는 것** (참조가 끊긴 것.  판정이 기계적입니다):

| 대상 | 조건 |
| --- | --- |
| `outputs/revN/` | `revision` 테이블에 `id=N` 이 없다 |
| `uploads/*.pdf` | 어떤 `job.pdf_path` 도 가리키지 않는다 |
| `diagnostics/*.zip` | 파일명의 job id 가 `job` 테이블에 없다 |
| DB 자유 페이지 | `VACUUM` — 행을 지우지 않습니다 |

**절대 지우면 안 되는 것**:

| 대상 | 이유 |
| --- | --- |
| `job` 행과 그 `item` 행 | 분석 결과 자체입니다 |
| `user_json` 이 있는 `item` | **사람이 판단한 값**.  다시 만들 수 없습니다 |
| `added=1` 행 | 사람이 넣은 행.  검출로 복원되지 않습니다 |
| `review_state` · `report` | 사람이 남긴 결정과 신고 |
| 살아 있는 `revision` 과 그 출력 | 리비전 비교의 대상입니다 |
| `feedback` | 다음 회차의 학습 신호로 쓰기로 한 것입니다 |

**언제**: 후보 셋.
- **서버 기동 시 자동** — 사용자가 아무것도 안 해도 정리됨.  다만 조용히
  지우므로, 무엇을 지웠는지 로그에 남겨야 합니다
- **버튼 하나** — 감사기가 "정리 가능 N MB" 를 띄우고 누르면 지움.
  폐쇄망 단일 사용자 환경에서는 이쪽이 예측 가능합니다
- **나이 기준** — "N일 지난 것" 은 **권하지 않습니다.**  근거가 없는 값이고,
  이 프로젝트에서 한 번 만든 산출물을 며칠 뒤 다시 여는 일은 흔합니다

**VACUUM 은 따로 봐야 합니다.**  168 MB → 15 MB 는 VACUUM 이 만든 것이고,
행을 하나도 지우지 않습니다.  다만 전체를 다시 쓰므로 큰 DB 에서는 수 초
멈춥니다.  기동 시가 아니라 **정리 버튼 안**에 두는 것이 안전합니다.

### (다) 애초에 덜 쌓이게

- **`revision` 을 만들 때 출력 디렉터리를 재사용**합니다.  지금은 `/revisions/N/excel`
  을 부를 때마다 `outputs/revN/` 에 다시 쓰는데, 같은 revision 을 두 번 내보내면
  같은 내용을 두 번 쓰는 셈입니다 (디렉터리는 하나이므로 개수는 늘지 않습니다).
- 43개 중 **`unmapped` 라벨 스냅샷은 UI 테스트가 만든 것**입니다
  (`test_step6_reports_unmappable_edits` 가 `POST /jobs/{id}/snapshot` 을 label
  `unmapped` 로 부릅니다).  즉 이 몫은 **원인이 테스트였고, 이번 회차의 격리로
  이미 막혔습니다** — 제품 경로의 문제가 아니었습니다.
- 이 항목은 *원인* 쪽이라 (가)·(나) 와 배타적이지 않습니다.

## 3. 권하는 조합 — 다만 정하는 것은 사용자입니다

**(가) 상시 + (나) 버튼**.  이유:

- 세는 것은 위험이 0 이므로 늘 켜 둘 수 있습니다.
- 지우는 것은 사람이 한 번 확인하고 누르는 편이 낫습니다 — 폐쇄망 단일
  사용자 환경이고, 이 프로젝트에서 되살릴 수 없는 값(`user_json`, `added`)이
  같은 파일 안에 있기 때문입니다.
- 기동 시 자동 삭제는 "조용히 사라진다" 는 성질이 있어, 이 도구가 지금까지
  지켜 온 원칙(무엇을 왜 했는지 항상 화면에 남긴다)과 어긋납니다.

(다) 는 위 둘과 무관하게 따로 볼 문제입니다.

## 4. 이번 회차에 이미 들어간 것

방침과 별개로, **재발 경로 하나는 이미 막혔습니다** — UI 테스트가 실 DB 를
쓰지 않습니다 (`PID_DATA_DIR` + 세션 사본).  이번에 치운 43개 중 다수가 그
경로로 쌓인 것이었습니다.
