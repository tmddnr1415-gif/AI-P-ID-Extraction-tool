## 0. 왜 이 회차가 생겼나 — `UI 21` 은 유효한 통과가 아니었다

갈음 검증이 UI 스위트를 **처음으로 10회차 이후 데이터에서** 돌렸고 2건이
깨졌다.  11·12·13 회차 회귀표의 `UI 21` 은 전부 **SCOPE 가 전부 빈칸인 DB**
에서 나온 값이다 — 그 상태에서는 모든 행이 `legacy` 로 분류돼 SCT 필터가
실질적으로 아무 행도 거르지 않는다.  필터를 시험한다고 적어 둔 시험이 필터가
꺼진 것과 같은 조건에서만 돌고 있었다.

실 DB 의 분석 4건을 세어 확인했다: **824 · 824 · 824 · 75행, SCOPE 전부 빈칸.**

파일 동일성으로는 잡히지 않는 종류였다 — 코드는 같고 **데이터가 달랐다.**

## 1. 시험의 가정을 사실에 맞춘다 (B)

### 무엇이 틀렸나

`edited` 픽스처가 FIELD **첫 다섯 행**을 집어 고쳤다.  순서에만 의존하고
그 행이 SCT 인지 보지 않았다.  새 분석에서는 첫 다섯 중 **3행이
`VENDOR(HRSG)`** 이고, 11회차부터 발주처 양식은 SCT 만 담으므로

- 고친 값이 양식에 안 실린다 → `test_step6_edits_reach_the_excel` 실패
- 이미 범위 밖인 행의 SCOPE 를 또 바꿔도 행수가 안 준다 (**667 → 667**)
  → `test_step6_scope_edit_removes_the_row_from_the_client_workbook` 실패

**제품은 맞았다.**  API 로만 재현해 확인했다: 대상 행이 이미 `VENDOR(HRSG)`
였고 스냅샷은 매번 새로 생겼으며(rev 3 → 4) `out_of_scope 249` 가 그대로였다.

### 어떻게 고쳤나 — 순서가 아니라 **상태**로 고른다

`field_rows` 픽스처가 FIELD 행을 세 갈래로 나눈다.  갈래는 화면
(`scopeFacts`)·서버(`excel_out.in_client_scope`)와 **같은 정의**다:

| 갈래 | 조건 | 양식에 |
| --- | --- | --- |
| `delivered` | `SCT` | 나간다 |
| `vendor` | 그 밖의 값 | 안 나간다 |
| `legacy` | 빈 값 | **나간다** — "판정한 적 없음"이라서 |

마지막 갈래가 뒤집힌 것처럼 보이지만 11회차가 그렇게 정했다: 없는 판정을
타사 공급으로 읽으면 발주처 양식 네 개가 통째로 빈 파일이 된다.

### 세 경우를 **모두** 시험한다 (신규 3건)

| 시험 | 무엇을 못박나 |
| --- | --- |
| `test_step0_the_suite_runs_against_scope_aware_data` | ★ 이 스위트가 **어떤 데이터에서 도는지** |
| `test_step6_edit_on_a_vendor_row_does_not_reach_the_client_workbook` | 벤더 행 편집은 화면·DB 에 남고 파일에는 안 간다 — **그것이 정상이다** |
| `test_step6_a_row_with_no_scope_is_written_not_dropped` | 빈 SCOPE 행은 담긴다 · `legacy_no_scope_rows` 에 세어진다 |

### 데이터 전제를 코드로 못박았다

`test_step0` 은 **건너뛰지 않고 실패한다** — 건너뛰기가 바로 그 침묵을 세
회차 동안 만들었기 때문이다.  옛 DB(824행 · SCOPE 전부 빈칸)에서 실제로
돌려 확인했다:

```
FAILED test_step0_the_suite_runs_against_scope_aware_data
  이 DB 에는 SCOPE 가 SCT 가 아닌 FIELD 행이 없다 - 10회차 이전 분석
  (SCOPE 전부 빈칸)으로 보인다.  다시 분석한 결과에서 돌려야 이 스위트가
  발주처 양식 필터를 실제로 시험한다
```

**결과: UI 21 → 24, SCOPE 있는 데이터(1029행 · SCT 667 / VENDOR 218)에서 전량 통과.**

## 2. 편집이 양식에 어떻게 닿는지 — 그 순간 말한다 (C)

### 결함

팀원이 벤더 행의 값을 고쳐도 발주처 양식에 반영되지 않는데 **화면이 조용했다.**
12회차가 근거 패널에 "발주처 양식에 나가는가" 를 넣었지만, 그것은 행을
**누른** 사람에게만 말한다.  칸을 바로 고치는 사람은 아무것도 못 본다.

### 판정은 한 곳에만 둔다

`scopeFacts(scopeVal)` 하나를 만들고 **근거 패널·저장 전 안내·저장 후 안내**
셋이 그것을 읽는다.  판정을 두 벌 만들면 언젠가 갈린다 (11·12회차가 같은
이유로 세 곳을 고쳤다).

### 세 갈래 · 두 시점

| 시점 | 무엇 |
| --- | --- |
| 저장 **전** (작성자 줄 위) | 이 행이 양식 밖이면 그 사실 — 고치기 전에 안다 |
| 저장 **후** (한 줄 안내) | 무슨 일이 일어났는지 |

실측한 문구 (`out/round14/capture.json`):

```
SCT 행      저장했습니다. 이 행은 발주처 양식에 나갑니다
벤더 행     저장했습니다. 이 행은 SCOPE=VENDOR(HRSG) 라 발주처 양식에는
            나가지 않습니다 (화면에는 남습니다)
legacy 행   저장했습니다. 이 행은 SCOPE 를 판정한 적이 없습니다 —
            다시 분석하면 정해집니다
SCT → 비SCT  발주처 양식에서 빠집니다 — 지금 779행
비SCT → SCT  발주처 양식에 들어갑니다 — 지금 780행
```

**막지 않는다.**  화면·DB 에는 남아야 하고, 그 행의 SCOPE 가 나중에 SCT 로
바뀌면 값은 그때 나간다.

### 행수는 서버가 센다

`GET /jobs/{id}/scope_summary` 를 새로 뒀다.  완료 화면이 쓰는 `_scope_summary`
를 **그대로** 부르고, 그 함수는 산출 필터 `excel_out.in_client_scope` 를 쓴다.
화면이 말하는 수와 파일에 들어가는 수가 갈리면 안 되기 때문이다.
삭제 표시된 행은 뺀다 — `write_all` 이 그 행을 먼저 거른다.

### 화면이 한 말이 파일과 맞는가 — 실제로 열어 확인했다

편집 세 개를 넣고 발주처 양식을 만들어 셀을 뒤졌다:

| 편집 | 화면이 한 말 | 파일에 |
| --- | --- | ---: |
| `UI-SCT-1` (SCT 행) | 나갑니다 | **있음** |
| `UI-VEN-1` (벤더 행) | 나가지 않습니다 | **없음** |
| `UI-LEG-1` (legacy 행) | 판정한 적 없음 | **있음** |

`legacy_no_scope_rows: 1` 로 세어졌다.  세 문장이 파일과 전부 맞는다.

### ⚠ 캡처가 잡은 결함 — 앞 편집의 안내가 남아 있었다

첫 캡처에서 **서로 반대인 두 문장이 동시에** 화면에 있었다: 앞 행의
"발주처 양식에 나갑니다" 가 남은 채로 다음 행의 "나가지 않습니다" 가 떴다.
둘 다 각자의 행에 대해서는 맞는 말이라 더 나쁘다 — 어느 행 이야기인지
화면이 말하지 않는다.  안내를 띄울 때와 이름을 물을 때 앞 것을 지운다.

**일곱 회차 연속으로 캡처가 결함을 잡았다.**

### ⚠ 고치지 않고 남긴 것 — `공급 주체` 가 편집값을 안 보여준다

`needs_review` 인 행의 SCOPE 를 고치면 근거 패널의 `공급 주체` 가
`검토 필요 ✎ 사람이 고침 (도면 근거는 SCT)` 이라고만 적고 **방금 넣은 값을
말하지 않는다** (SCOPE 열에는 `VENDOR(캡처 시험)` 이 보인다).  12회차가
정한 문구라 이 회차에서 바꾸지 않았다.  바로 아래 `발주처 양식` 줄이
`나가지 않습니다` 로 결과는 정확히 말하므로 팀원이 판단할 정보는 다 있다.
**다음 회차 후보.**
