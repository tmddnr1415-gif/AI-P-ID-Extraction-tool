**최신 기록이 위쪽**에 옵니다.

기록은 `scripts/apply_feedback.py`가 리뷰 UI의 피드백 JSON을 받아 자동으로 추가합니다.

```bash
python3 scripts/apply_feedback.py feedback_run_20260815_2230.json --apply-rules
```

각 항목에는 **언제 · 누가 · 무엇을 · 왜 고쳤는지**와 **앞으로 어떻게 출력되어야 하는지**가
함께 남습니다. 규칙 코멘트는 `rules/extraction_guide.md` 하단에 초안으로 쌓이며,
사람이 문장을 다듬어 본문 절로 승격시킵니다.

### 1차 결과 — 정답을 보지 않고 판독

| 항목 | p6 | p20 | p38 |
|---|---|---|---|
| 행 수 | 12 / 12 | 33 / 33 | 24 / 24 |
| TYPE | 100% | 100% | 100% |
| INST. TYPICAL TYPE | 100% | 100% | 100% |
| Q'ty | 100% | 100% | 87.5% |
| DESCRIPTION (완전일치) | 0% | 18% | 0% |

행 수·TYPE·TYPICAL은 전부 맞았다. **DESCRIPTION만 69행 중 6행**이다.
계기를 찾는 것보다 **부르는 이름을 맞추는 것**이 어렵다는 뜻이다.

### 정답 대조로 확인한 것

1. **`*` / `**` 공급 범위 표기가 최대 제외 사유.** p6은 계기 문자 34건 중 22건이
   `* DENOTES ... SUPPLIED BY HRSG` / `** ... BY ST SUPPLIER` 라서 빠지고 12건만 남는다.
   이 각주를 못 읽으면 행 수가 3배가 된다. → 규칙 3.1 신설
2. **`CONFIGURATION IS IDENTICAL FOR ...` 는 행 분리가 아니라 Q'ty 배수.**
   `GROUP#20` → 2, `UNIT#12,21,22` → 4. → 규칙 5.1 신설
3. **`PLANT COMMON` 설비는 그 배수에서 빠진다** (qty 1). p38 Q'ty 오차 3건이 전부 이것.
4. **도면 안 병렬 계기는 합치지 않는다.** FE 1개 + FIT 2개 = 3행. → 규칙 5.2
5. **A/B가 두 자리에서 뜻이 다르다.** 설비명 뒤 = 어느 설비, 문장 끝 = 같은 지점의
   몇 번째 계기. `PUMP A SUCTION PRESSURE B`. → 규칙 6.1
6. **설비 이름은 그 도면 설비 박스에 적힌 대로.** p20은 `BOILER FEED WATER PUMP`,
   p38은 `BFP A/B COOLER`. 같은 설비라도 도면이 다르게 부르면 다르게 쓴다. → 규칙 6.2, 6.3
7. **공용 헤더는 설비 서브 식별자를 뺀다.** → 규칙 6.4
8. **구간 이름은 배관 치수가 아니라 도착지에서.** `MINIMUM FLOW RECIRCULATION LINE` 이라
   적힌 라인의 유량계도 정답은 `DISCHARGE IP FLOW` 다. → 규칙 6.5
9. **그룹 공용 계기는 그룹 번호를 호기 자리에** (`UNIT #10`). → 규칙 6.6

## 2026-08-16 — NOTES 영역 오류 발견 및 무API 기준선 강화

- 발단: "API 과금이 부담스러운데 호출 없이는 제대로 안 나오나"

### 발견 — 모델이 NOTES를 본 적이 없다

`pdf_to_images.py` 와 `web/pdfscan.js` 둘 다 NOTES를 **좌상단**(`x < 0.22`)에서 뽑고
있었다. 실제 이 도면들의 `GENERAL NOTES` / `NOTES` 는 **우상단 x ≈ 0.83** 에 있다.

즉 프롬프트에 들어간 "도면 NOTES" 는 좌측 배관 라벨 쪼가리였고, 판독의 핵심 근거인

- `* DENOTES EQUIPMENT WILL BE SUPPLIED BY HRSG.`
- `THIS P&ID IS FOR GROUP#10, CONFIGURATION IS IDENTICAL FOR GROUP#20.`

를 모델은 **한 번도 받지 못했다**. 어제 규칙 3.1과 5.1을 새로 쓰고도 정작 그 판단에
쓸 입력이 안 들어가고 있었던 셈이다.

좌표를 고정하는 대신 `GENERAL NOTES` / `NOTES :` 글자를 찾아 그 아래·오른쪽을 딸려
오도록 고쳤다. 못 찾으면 우상단을 넓게 훑는다. 세 도면 모두 각주 원문이 들어온다.

### 무API 기준선을 5개 컬럼까지 채우도록 강화

기존 기준선은 TYPE별로 개수만 세어 한 줄로 묶은 것이라 쓸모가 없었다. 도면에서
결정적으로 읽히는 것을 모두 채우도록 바꿨다.

| 컬럼 | 근거 |
|---|---|
| `SYSTEM` | 도면 제목 ↔ 템플릿 SYSTEM 목록 단어 일치율 0.6 이상 |
| `P&ID No.` | 타이틀블록 |
| `TYPE` | 텍스트 레이어 계기 문자 매핑 |
| `Q'ty` | NOTES `IDENTICAL FOR ...` 의 호기 개수 + 1 |
| `INST. TYPICAL TYPE` | **계통+TYPE별** 템플릿 최빈값 |

TYPICAL은 TYPE만 보면 TIT-3(53건)과 TIT-5(46건)가 반반이라 동전 던지기였다.
계통을 함께 보니 HP Steam → TIT-3, Feedwater → TIT-5 로 정확히 갈렸다.

실측(p6/p20/p38): SYSTEM·P&ID No.·TYPE 전부 일치, Q'ty p6·p20 일치·p38 21/24,
TYPICAL 전부 일치. 행 수는 p38 24/24 정확, p6 34행(정답 12 — 공급 범위 22행이 남음),
p20 35행(정답 33 — PDIT 2행이 남음).

`*` 표기는 텍스트가 아니라 도형이라 자동 검출을 시도했으나 오검출이 심해 접었다.
대신 그 도면의 공급 범위 각주 **원문을 `확인 필요` 에 그대로 띄워** 사람이 지우도록 했다.

### 비용

판독 전에 예상 입력 토큰을 보여 준다. 도면당 약 54k(타일 3x2·200dpi)이고 대부분이
이미지다. 2x2·150dpi로 낮추면 약 20k. 계기 문자는 텍스트 레이어에서 정확히 오므로
타일 해상도를 낮춰도 계기를 놓치지는 않는다 — 다만 설비명 판독이 나빠질 수 있어
낮춘 설정으로 정확도를 다시 재야 한다.

### 다음에 할 것

- NOTES가 들어간 상태로 API 판독을 돌려 규칙 3.1/5.1이 실제로 먹히는지 확인
- 2x2·150dpi 설정에서 정확도가 얼마나 떨어지는지 측정


## 2026-08-16 — DESCRIPTION 무API 자동 생성 시도 및 기각

- 발단: "API 없이 DESCRIPTION을 읽을 방법은 없나"

재료는 텍스트 레이어에 다 있다. 설비 박스 이름, 배관 행선지, 측정 대상(TYPE에서),
호기 번호. 계기 좌표에서 가장 가까운 라벨을 주워 `호기 + 설비 + 계통약어 + 구간 +
측정대상` 으로 조립하는 방식을 만들어 정답과 대조했다.

| 시도 | 완전일치 |
|---|---|
| 1차 (가까운 라벨 그대로) | 3 / 69 |
| 2차 (도면번호 제외·단수화·A/B 제거·계통명 대체) | 0 / 69 |
| 3차 (거리 임계값 6종 × x가중치 3종 그리드) | **최대 6 / 69 (9%)** |

p38(갈래마다 설비 박스가 있는 도면)에서만 6건이 맞고 p6·p20은 0건이다. 이유가 분명하다.

- p20 정답 `UNIT #11 BOILER FEED WATER PUMP A DISCHARGE HP FLOW A` — 도면에
  `BOILER FEED WATER PUMP` 라는 글자가 없다(`FEEDWATER PUMP FOR HRSG UNIT #11`).
  `DISCHARGE HP` 는 그 배관이 HP 이코노마이저로 간다는 걸 따라가야 나온다.
- p6 정답의 `HP STEAM` 은 설비명이 아니라 계통 제목이고, `DRAIN` 은 그 DN300 배관이
  드레인이라는 판단이다.

어느 라벨을 고를지와 뭐라고 부를지가 곧 판독이다. 좌표만으로는 안 된다.

**기각 결정.** 9% 정확도의 문장을 그럴듯하게 채워 넣는 것은 안전 관련 문서에서
위험하다. 문장을 지어내지 않는다.

**대신 채택.** 계기마다 가장 가까운 설비명과 배관 행선지를 `근거`(source_tokens)에
붙인다. 사람이 도면을 다시 뒤지지 않고 검토 UI에서 DESCRIPTION 을 쓸 수 있다.
`'PI' @ x=0.28 y=0.28 · 설비 '#11 BFP A/B COOLERS' · 배관 'FROM GROUP#20 CCW SUPPLY'`

### 곁가지로 확인한 것

DESCRIPTION 이 도면 사이에 재사용되는지도 봤다. 563행 중 서로 다른 문장이 486개,
**2개 이상 도면에 걸쳐 나오는 문장은 2개(5행, 1%)** 뿐이다. 앞 도면 결과로 사전을
만들어 뒤 도면을 채우는 방법도 성립하지 않는다.

→ DESCRIPTION 은 도면마다 모델이 읽어야 한다. 이건 우회로가 없다.
